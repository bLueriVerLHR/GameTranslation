# 经验库 · 翻译

本文收录翻译提取、写回与烘焙、验收普查、插件参数文本、分块批次相关的踩坑与
判据。流程定义见 `docs/translation.md`，数据契约见 `docs/translation-data.md`，
QC 与故障排查见 `docs/translation-qc.md`。其他主题经验见
[打包与清理](experience-packaging.md) · [Tyrano](experience-tyrano.md) ·
[杂项](experience-misc.md) · [经验库索引](experience.md)。

术语：**键表**是提取出的可译串集合（`keys.jsonl`）；**译文库**是按 id 落盘的
译文集合；**烘焙**（bake）是把译文库按 id 写回游戏数据；**预填**（prefill）
是用随包字典机械填入译文；**门禁**（gates）是五道结构校验（覆盖、控制码、
假名残留、换行数、待决）。

## 1. 提取范围

### 1.1 覆盖率只说明已提取的子集是完整的

**现象**：v2 全量跑完、五道门禁全绿（`coverage 0 missing`），构建里说话人
名栏仍是日文（`豊聡耳神子`）。原因不是翻译质量，而是提取器漏字段：`101`
命令的 `parameters[4]`（名牌）从未进过键表。

**判据**：门禁与覆盖率只对**已提取子集**成立。扩展提取器后同一款游戏又补出
13,321 键（名牌 10,296、`657` 续行 1,964、`402` 分支标签 451、`357` 插件
文本 404、DB 206）。

**处置**：

- 验收硬指标是「最终构建里没有日文」，不是门禁绿。在**烘焙后的构建**上扫描
  `data/*.json` 的每个字符串，用假名字母类（定义以 `translation/codes.py` 的
  `KANA_LETTERS_RE` 为准：`\u3041-\u3096`、`\u30a1-\u30fa`、`\uff71-\uff9d`）。
  `・`（U+30FB）、`ー`（U+30FC）与半宽长音符 `ｰ`（U+FF70）是中文保留项，计入
  会得到 4,429 条假阳性。
- 重提取必须从**日文原始数据**做，不能从已烘焙的中文构建做：已译句可能不含
  假名与汉字（纯 `——`、`……!`），提取器会把它当非文本并丢掉 id（实测丢
  23 个 id）。重提取要断言「旧 id 集 ⊆ 新 id 集」。
- 新类别可机械预填：同日语原文已在库里译过就复用（实测 6,983 条：名牌
  6,532 加分支标签 451）。`402` 分支标签应与同组 `102` 选项译文逐字一致
  （按选项索引配对）。预填仍走 `append` 提交，控制码校验兼作正确性检查。
- 插件指令（`357`/`657`）的参数是标识符与散文混合：插件名、命令名、JSON
  参数对象、路径、脚本片段不译，只有读出是散文的字符串进键表。
- DB 战斗台词（`message1`/`message2`）含 `%1`/`%2` 占位符，逐字保留。
- 第二轮重提取又拖出两类。插件指令参数**对象内部**的字段
  （`{"messageText": "叫び声が響く……"}` 弹窗文本、`{"text": "Shift 键快进"}`
  界面提示）只看顶层字符串会全漏；整行半宽片假名（`ﾌﾞﾂﾌﾞﾂ……`）在假名类
  不含半宽块时被当「无假名」丢弃。残留扫描的假名类必须与提取器同一份定义
  （`translation/codes.py` 的 `KANA_RE` 与 `KANA_LETTERS_RE`），并把残留
  分成「有意跳过的内部字段」与「意外残留」：后者非零即真缺口。扫描脚本以
  退出码表达结论，可当门禁跑。

### 1.2 「有意跳过」清单本身是风险源

**现象**：被归为「编辑器内部名、跳过」的 `System.json` `switches` 与
`variables` 的**名字**，被变量窗口插件
`drawText($dataSystem.variables[id])` 画在界面上，是玩家可见的日文。

**判据**：跳过清单的每一类都要到插件代码里核实。在成品 `js/`（含插件）里
搜索该字段的读取模式（`MapInfos`、`CommonEvents[..].name`、
`$dataSystem.variables`），命中的再读上下文：写进 `drawText` 或赋值给可见
对象的要提取，只按 id 取数据的不用。

**处置**：实测构建中 `MapInfos`、`CommonEvents`、`Tilesets` 的 `name` 无任何
插件读取，是内部名；`switches` 与 `variables` 的名字要提取（引用一律走 id，
改名安全）。残留扫描的跳过清单必须随提取器同步收紧，否则「0 意外残留」是
假阴性。

### 1.3 运行期文本键 `\T[键]`

**现象**：构建能跑，但开始菜单显示原始键（`\T[SIS1036]` 而不是「新游戏」），
`data/*.json` 与 `js/plugins.js` 里全是 `\T[键]`（一款大型 MZ repack 实测
7,176 个键、14,507 处）。此时门禁全绿、覆盖率 100%：键是纯 ASCII、零假名，
提取器不当文本，假名门禁也看不见。

**判据**：网页构建里没有任何东西解析键。游戏自带的多语言插件
（`Chimaki_Lang` 一类，报头写着 `Configure multilingual by using CSV file
v1.2`）用 Node 的 `fs.readFile('./csv/UI.csv')` 读文本表，浏览器里没有
`fs`；MTool「挂载翻译」（根目录 `MTool挂载翻译.txt` 标记）在运行时用随包
字典替换键，清理 MTool 之后没有替代者。把该插件的 `status` 改 true 会让标题
画面立刻抛
`TypeError: Cannot read properties of undefined (reading 'SIS1036')`（文本表
在浏览器里永远加载不出来），不要试图重新启用它。

**处置**：构建期落地，用 `tools/resolve_text_keys.py`，它已接进
`tools/bake_translation.py`（`--no-text-keys` 关闭）。数据源优先级如下：

1. 游戏自带 CSV 文本表的 `cn` 列（`csv/UI.csv` 的列序 `id,who,tw,cn,en`，
   `tw` 装日文原文）；
2. 随包字典的术语行（`ID,分类,日语,中文,English`，取 id 之后**最后一个含
   CJK 且无假名**的字段，能躲开日文分类列与英文列）；
3. 该 id 的日文经字典的 `{日文:中文}` 平配对译；
4. 只剩日文时用日文（比在屏幕上显示键好，且计数可见）；
5. 全都没有时原样保留并报告（`--strict` 变非零退出）。

配套约定：

- **只改显示文本**：字段判定复用 `tools/qc_build_kana.py::classify`（资产名、
  地图事件名、`note`、`357` 派发键、System 资源字段豁免），两个工具不会各自
  漂移。
- **转义层级是第二个坑**：键在嵌套 JSON 参数里每多一层 `JSON.parse` 就多一层
  反斜杠（`\T[id]`、`\\T[id]`、`\\\\T[id]`，`QuestDatas` 这类三层参数实测
  存在）。必须吃下**整段**反斜杠，再按 `len(run) // 2` 把插入的文本重新
  转义；只吃两个反斜杠会留下 `"Title":"\\药草采集"` 这种非法转义，游戏开机
  直接 `SyntaxError: ... is not valid JSON`。工具的 `json_layers()` 在改写
  前后对比「有多少字符串还能被 `JSON.parse`」，退化即 WARN。
- **验收门禁**：`qc_build_kana.py` 的 `text_keys` 类，显示文本里残留
  `\T[键]` 即判失败（依据同一份 `translation.codes.TEXT_KEY_RE`）。作者表格
  里本来只有日文的行按 `source_table` 单列，只报不判失败（表内单元格先剥掉
  控制码再比对，事件会在键两侧加码），否则部分翻译的 repack 会让门禁永远红。
- **实测量级**（一款 MZ repack）：14,153 处 → 表格中文列 65.1%、字典术语
  10.4%、字典日文对译 10.9%、只能回退日文 13.6%、原包也没有文本 0.05%
  （7 处，原 repack 自己也只显示键）。

结论：门禁全绿加覆盖率 100% 只证明已提取子集译完；构建能不能显示中文，必须
在真构建上跑 `qc_build_kana --source`，并在浏览器里看一遍。

### 1.4 MV 的对话在 CSV（`ExternMessage.csv`）

**现象**：`tools/translate_rpgmaker.py` 原本只烘焙 `data/*.json`，开场场景
保持日文；贪心翻译器还会重写 `\M[...]` 里的 ID，破坏 CSV 查找。

**判据**：有些 MV 游戏带 UTF-16LE 的 `data/ExternMessage.csv`（列
`名前(ID),本文(body),…`），事件里只有指向它的 `\M[ID]` 引用。

**处置**：`translate_text` 保护控制码括号（`\M[ID]`、`\V[1]`、`:name[...]`
等），只翻译它们之间的纯日文片段；`:name[NAME,FACE]` 的 NAME 是显示文本
（已确认 `:name` 参数与 CSV id 不冲突）。`translate_extern_csv` 逐行翻译
「本文」列，ID 保持不动，保留 UTF-16LE/BOM（或 `utf-8-sig`/`cp932`）与
CRLF。修复后必须从源重跑整条流水线，旧构建的 `\M[...]` 引用已损坏。

翻译后校验 CSV ID：地图 JSON 里每个 `\M[ID]` 都要在 CSV 的「名前」列存在；
`\V[320`、`テスト`、单假名这类既有缺失来自源数据，不算新缺口。

### 1.5 repack 不等于已烘焙

**现象**：一款 MV repack 的数据已翻译，另一款在游戏根带 MTool 字典而
`data/` 仍是日文。

**判据**：检查数据文本是否仍含假名，不要假设「repack 就是已烘焙」。

**处置**：自己烘焙，
`python -m tools.translate_rpgmaker <built> <out> --trs "<title>.json"`
（实测 7,742 条）。该类 repack 还会向 `css/game.css` 追加 CJK 字体回退；
烘焙后重跑假名普查。`translate_rpgmaker.py` 只写数据文件，JSON 以 `indent=2`、
`ensure_ascii=False`、无 BOM 写盘；它也可以由 `translate_data` 直接烘焙进构建。

### 1.6 图像里的日文不译

**现象**：标题 logo、UI 贴图、横幅、漫画式文字等烧进图片的日文，全树字节
搜索找不到。

**判据**（一条选择肢窗口上方的风格化日文横幅的判定过程）：

1. 全树字节搜该串（UTF-8、CP932、UTF-16LE、`\uXXXX`）⇒ 0 命中；
2. 运行时搜变量、事件名、插件参数 ⇒ 无；
3. 隐藏所有 `Sprite_Picture` 仍在、隐藏 `WindowLayer` 才消失 ⇒ 是窗口画的；
4. 文本却不在任何数据与 JS 里 ⇒ 只能来自运行时构造或图片合成。

**处置**：认定为美术资源，不在翻译范围，不重画。前三步必须先做，才能区分
「美术」与「真漏译」：数据里的文本能改，图片里的不改。

## 2. 写回与烘焙

### 2.1 消息块的多行上下文

**现象**：连续 `401`/`405` 命令实际是一条消息，逐行翻译会拆坏句子。

**判据**：`\n` 拼成的整条消息是单个键；菜单帮助文本属同一类多行块。

**处置**：烘焙器拼接同一段，再按命令把值拆回去：短值补 `""` 行，多余行追加
为新命令。

### 2.2 按名称查找的引用只翻一边会坏

**现象**：翻译构建启动、地图渲染，但玩家永远无法移动。`canMove()` 保持
false，因为 `$gameMap.isEventRunning()` 恒 true；地图解释器空闲
（`running=false`、`index 0/0`），事件 1 每帧卡在 `_starting=true`。

**根因**：`TemplateEvent.js` 把 Note 含 `<TE:name>` 的事件换成模板事件，在
模板地图（插件参数 `TemplateMapId`）里**按名查找**：

```js
generateTemplateId: templateId = findMetaValue(event, 'TE')
    -> searchDataItem($dataTemplateEvents, 'name', templateId)
```

模板地图持有短「setup-and-erase」模板列表（5 条命令对原 23 条）。翻译把模板
地图的事件**名**译成中文，而每个 Note 的 `<TE:マップ初期処理>` 保持原样 →
按名查找失败 → 模板永不应用 → 原无条件 autorun 事件（永不自我擦除）每帧
重触发 → `isEventRunning()` 恒 true → 移动锁死。

**判据**：关键运行时差异不在数据结构或插件文件（除译文字符串外字节一致），
而在**运行时状态**——对比两个构建的
`Game_Event._erased/_starting/_pageIndex`。原版事件 `erased: true`（模板列表
跑完擦除）；翻译构建恒 `erased: false, pageIndex: 0, trigger: 3`。用 trace
插件记录 `interp.setup listLen`、`EVENT.start`、`eraseEvent`：原版用
`listLen=5`（模板）setup，翻译构建总用 `listLen=23`（原版列表）。

**处置**：`tools/bake_translation.py` 的 `_translate_note_refs()` 用同一精确
匹配字典把 `<TE:ja>` 改成 `<TE:zh>`（跳过 `\v[1]` 类控制码引用），再从干净源
副本重烘焙；旧构建上的手工 note 编辑会被之后的烘焙覆盖。

同一处还修了 `bake_translation.py` 曾以 `encoding="utf-8-sig"` 写所有
`data/*.json`（写入 BOM）——改为纯 `utf-8`，因为 `System.json` 里的 BOM 会
破坏引擎的 `JSON.parse`。

**推广**：翻译前扫描插件里按名称查找的模式（`<TE:`、`@command` 名引用、
`PluginManagerEx.findMetaValue`）。任何按显示名解析实体的插件（模板事件、
气泡名、`callEventByName`、选择帮助标签）在查找只有一侧被翻译时坏掉。

### 2.3 `note` 标签载荷只翻一边会把道具从菜单里弄没

**现象**：一款 MZ 游戏的道具菜单有自定义分类页签。插件把页签名放在插件参数
`categoryList` 里，道具在 `note` 里用 `<itemCategory:…>` 标记自己的分类，
两者**按名逐字匹配**：

```js
Window_ItemList.prototype.includes = function (item) {
  if (item && item.meta.itemCategory) return this._category === item.meta.itemCategory;
  return _Window_ItemList_includes.call(this, item);
};
```

翻译把插件参数译成中文（它确实是显示文本），而 `note` 里的标记保持日文
（提取器有意不碰 `note`，因为那里绝大多数是插件命令、内嵌 JSON、查找键）。
`_category` 与 `item.meta.itemCategory` 永不相等，而这批道具带标签又不会落回
普通分类，于是**在道具菜单里彻底消失**。门禁全绿，启动与文本层面看不出任何
异常。

**判据**（可复用的发现手法）：

1. 在最终构建上跑假名普查，按 **JSON 路径**分类每一条命中：
   `parameters[2]`（`357` 的 `@text`）、`657` 回显、`MapInfos[].name`、
   `Animations[].name`、`note`…绝大多数属于「有意不提取」。
2. 剩下的 `note` 命中里，凡是**载荷是散文**（含假名且不是纯数字或坐标）的，
   逐条问「这个插件会把它画出来吗」：去 `js/plugins` 里搜标签名，看它把载荷
   当**标签**（要翻）还是当**键**（不能单边翻）。
3. 只要插件把载荷与**别处的字符串**做比较或查找，就把那个「别处」也搜出来
   （插件参数、事件注释、另一个 `note`）——**两边必须同译或同不译**。

**处置**：`note` 仍默认整体不提取（安全默认），改用显式白名单打开：

```bash
python -m translation.cli prepare <game_dir> <work_dir> --note-tags 拡張説明,itemCategory
```

- 白名单由调用者给出，工具里不硬编码任何游戏数据。
- 每个标签**每次出现**一个键，id 形如
  `data/Items.json#[12].note#itemCategory[0]`（DB 记录）或
  `data/Map172.json#events[1].note#LB[0]`（地图事件，两类 `note` 都扫）；出现
  序号保证唯一且稳定，同一 `note` 里重复的标签不会撞键。`ja` 只含**载荷**，
  标签名不进键。
- 载荷不含假名与汉字（纯数字、坐标、布尔）时自动不算文本，那是配置。
- `bake` 只替换**该次出现**的载荷：标签名与同一 `note` 里的其它标签逐字节
  不动；译文含 `<` 或 `>` 时**拒写并报 skip**（会破坏标签语法），不静默写坏。
- 重复烘焙是幂等的（位置寻址），但 id 漂移（标签被删或挪位）必须报 skip，
  不能猜。
- 提取的标签清单写入 `stats.json` 的 `note_tags`，事后可查打开了哪些标签。

**普查「还有哪些 `note` 标签在显示」**（替代表内枚举）：扫全构建
`data/*.json` 里所有 `<tag:...>`，按标签聚合载荷；只留载荷**含假名**的标签；
对每个标签去 `js/plugins/` 找引用它的插件，读它把载荷当显示文本还是查找键。
跑完剩下的应为 0，不为 0 的就是下一个同类事故。

`<LB:名字>`（事件头顶的地图标签）的载荷是纯显示文本，但它住在**地图事件的
`note`** 里，不在 DB 记录里，所以提取器要同时扫两处。帮助窗扩展
`<拡張説明:…>` 与 `<LB:…>` 这类无匹配风险的载荷用同一个开关一并解决（同一款
游戏实测 18 加 8 处）。

结论：插件的「按名匹配」不止发生在插件参数之间，也发生在插件参数与数据文件
之间。翻译前先 `rg` 那个参数值，看它是否又出现在 `data/*.json`（含 `note`）
或事件注释里，出现在哪就必须一起翻。门禁全绿仍不是交付判据：必须在最终构建
上做假名普查加路径分类。

### 2.4 覆盖率闸门与口径

**现象**：覆盖率闸门曾以烘焙遍历时的 hit/miss 为口径，而那次遍历还查两类
东西：它先试的「整块拼接键」（`行1\n行2`，然后才逐行回退），以及 `mvkeys`
有意跳过的非显示串（动画名、事件名等）。两者都不属于翻译流程，分母因此被
撬高：一款键表已覆盖 80% 的 MZ 游戏，闸门只报 7.3%
（`coverage: 1535 hit / 19555 missed`）；拆开看未命中的 95.7% 是被跳过的
非显示串、3.4% 是整块拼接。这份翻译**永远无法**通过 50% 闸门，只能一直
`--force`，闸门失去意义。

**判据**：口径改为对 `translation.mvkeys.keys_of()` 的**键表**计量
（`coverage: N/M keys translated = X%`，一条 key 一票），与
`translation.cli status` 报的百分比同口径。跳过的串照旧不翻（它们不是显示
文本），只是不再计入分母。

**处置**：低于 `--min-coverage`（默认 0.5）拒绝烘焙并指引全量翻译，
`--force` 覆盖（用于刻意的阶段式收割）。低覆盖烘焙等于半日半中，会污染后续
补翻。实测两款部分汉化 MV repack 的补翻构建覆盖率为 83.8% 与 89.8%，未触发
闸门。

### 2.5 烘焙工具的两处实测缺陷

**缺陷一：插件参数名不能限定为 ASCII**。路径解析器把名字限定成 ASCII 标识符
时，日文参数名与含空格的参数名会抛 `BakeError`，而它抛在 try/except **之外**
→ 整个烘焙中断而不是跳过。名字应允许除 `.`、`[`、`]` 之外的任何字符，且只能
出现在路径开头或 `.` 之后（畸形路径仍当错误）。

**缺陷二：「是否有字体切换插件」不能对 `plugins.js` 做全文文本匹配**。
`status: false` 的条目也被算作启用，于是本可做 CSS `unicode-range` 拆分的构建
被跳过拆分（假名面从未声明，全部字形回退到同一个中文字面）。改为解析
`plugins.js` 后**只看 `status` 为真**的条目；文件不可解析时保持保守（当作有
插件）。

### 2.6 译文库的尾部换行

**现象**：`translation/rawlib.py::read_library` 曾把值尾部的换行
`strip("\n")` 掉，于是**源文以换行结尾的键永远无法满足**（MZ
`data/Items.json` 的 `description` 就是这种字段）：写入时值丢一行 →
「换行数一致」门禁报 `source 1 -> value 0` 而整批拒绝，键进不了库 →
「覆盖」门禁（每键需非空）永远不绿。

**判据**：实测一款 MZ 游戏有 10 个键卡在这里。

**处置**：头行之间的文本**原样保留**（写方为空行的那一行就是真的尾部换行）；
手写批次尾部多余的空行不再被静默吞掉，会作为多一行被门禁报出。

### 2.7 identity 值是两种漏译的藏身处

**现象一**：假名门禁只抓**带假名**的残留，`bake` 也只剔除
「identity 且含假名」的条目，**纯汉字同形**的值既过门禁也不被剔。多数合法
（`男`、`女`、`魔女`、`防御`、`命中率`、`道具` 中日同形），但日文专用词会
静默留在游戏里（`購買`、`塩味`、`価格`）。

**现象二（字典预填）**：字典里的 identity 条目（`v == k`）SHADOW 逐行
fallback——带 identity 预填值的块键会让块查找先赢，两行保持日文，尽管有合法
的逐行片段翻译（第 1 行纯汉字时连假名残留扫描都看不见）。

**判据**：

- 纯汉字日文的唯一暴露点是 `value == key` 的条目：逐条过目 identity 清单
  （实测单轮只有 11 个 distinct 值，人工可过）。判定标准是「这个词在中文里
  也这么写吗」，不能改成机械规则。
- 清单的过滤条件要写对：含 ASCII 的分支标签
  （`en(v[12]>=1)根岸里美　if(!s[222])`）与含假名的串都不该进清单，否则淹没有
  效信号（含假名的串已由残留扫描覆盖）。
- `qc_build_kana --source` 把「与原版逐字节相同且无假名」的构建串列为
  **review**，永不判失败：共享字形人名（`根岸里美`）合法地相同，所以这是
  复核清单而非失败判定。

**处置**：从最终字典删掉每个 `v == k` 条目再重烘焙（实测删 123 条，全属
豁免类；残留从 24 降到 21，真未译行消失）。identity 清单要对照本游戏的
`decisions.md` 人名表逐条复核。

### 2.8 烘焙后必须回读比对

**现象**：`tools/rpgmaker_constants.py` 的 `SYSTEM_TEXT_FIELDS`（烘焙与旧
提取器共用的 `System.json` 字段表）与提取器
（`translation.mvkeys._SYSTEM_KEYS`）漂移：写成 `element`（真名是
`elements`）、完全没有 `gameTitle` 与 `currencyUnit`，却带着只属于 VX Ace 的
`message` 与 `commands`。后果是**静默**的：这些串被提取成键、被翻译、过五道
门禁、算进覆盖率，而 `bake` 从没写进构建——一款 MZ 游戏在「100% 覆盖」下
交付了日文标题与日文属性名（`ドラゴンディア`、`ドラゴン`、`アンデッド`）。

**判据**：门禁全绿证明不了「构建真的改了」。烘焙后把译库每个键的 JSON 路径
在构建里解析回来逐条比对，不一致当失败处理。

**处置**：两张表对齐（`tests/test_system_fields.py` 钉死一致），并把逐键
回读比对作为烘焙后验收的一环。

## 3. 插件参数文本

### 3.1 巨型参数走叶子级翻译

**现象**：`>300` 字符的 `kind=plugin` 键里，18 个键占 20.6 万字符（最大
83 KB，技能动画表、菜单模板等），整串翻译不可行。

**判据**：插件 JSON 的功能键（`位置X`、`テキスト名`、`条件`、`アニメ名` 等）
必须保持日文；叶子收集只取 VALUE，但最终假名残留扫描会报这些「键里的假名」，
属正常，勿修。字体名与样本文件名字面值（`07鉄瓶ゴシック.woff`、
`サンプル/一言_1`）必须进 `--exempt`，否则叶子翻译会改坏引用。事件 `note`
里的插件标签（`<BFC_座標:...>`、`<CounterExt:...>`）是功能数据，从模板剔除，
烘焙后保持原样。

**处置**：从模板剔除这些键，改走 `tools/plugin_json_leaves.py`：`extract`
（204 叶子）→ 叶子翻译（一个执行者）→ `rebuild`（23 个 blob 变更）→
`plugin_blobs_translated.json`。v2 的译文库不含插件键，所以该工具另有
`apply`（读 `plugin_blobs_translated.json`，复用 `translation.bake` 的
`plugins.js` 读写），**跑在 translation `bake` 之后**；原串在 `plugins.js`
里找不到的「死配对」会拒绝写入——那意味着叶子译文注定无效，静默写下去等于
假装完成。把**叶子**当键塞进 `plugin_blobs_translated.json` 也是错的（该文件
按**整段参数字符串**配对），会报 `dead pair` 并整批拒写。

### 3.2 显示键的大小写不统一

**现象**：窗口构建类插件（`ExtraWindow` 等）把窗口标签存在 JSON-in-JSON 的
`WindowList` 参数的 `Text` 字段里（值也是嵌套 JSON 字符串）。
`plugin_json_leaves.py` 的 `DISPLAY_KEYS` 原本只有小写 `"text"` 而没有大写
`"Text"`，这类窗口从未进工作清单，漏掉玩家可见的 HUD 标签。

**判据**：实测漏掉的值是 `引換券所持数\V[12]`（HUD 计数标签）与含 `園田晴香`、
`宝来玲緒奈` 的好感度窗口。按「键名包含 `Text`/`Title`/`Name`/`Message`」的
宽匹配收集、再用 `--exempt` 剔功能项，比穷举白名单安全。

**处置**：给 `DISPLAY_KEYS` 补上大写 `Text` 后，标准链路端到端可用：在修复前
的真实 `plugins.js` 上跑 `extract`（167 叶子，含 `引換券所持数\V[12]`，参数
`WindowList`）→ `rebuild`（1 个参数级配对，0 死配对）→ `apply`（applied 1，
0 死配对，118 插件仍可解析，日文标签消失）。

### 3.3 插件参数的豁免按「插件加参数」分类

**现象**：`plugin_json_leaves.py extract` 会捞到 UI 皮肤、样式、动画的
**标识符**（菜单皮肤插件按名精确查找）、SE 文件名、按键名、脚本里调用的插件
命令名。

**判据**：这些全部必须进 `--exempt`，否则译了菜单皮肤会失效。豁免文件是
**每游戏本地产物**，不入库。

**处置**：按 `(plugin, param)` 机械生成 `exempt.json`，再用
`extract --exempt` 复核剩余叶子数（实测 217 降到 60，剩下的全是成就馆、
图鉴、存档界面等真显示文本）。

### 3.4 插件命令参数里的资源文件名

**现象**：`357` 插件命令参数里形如 `.Image`（远景图文件名）、`.name`
（SE 文件名，如 `決定ボタンを押す7`）的参数看着像文本，其实是游戏内文件名，
译了就静默失效（远景图或音效消失）。

**判据**：与游戏内真实资源文件同名的字符串不是文本——`img/parallaxes/<v>.png`
或 `audio/se/<v>.ogg` 存在即说明。这类值在键表里是假文本。

**处置**：值写 identity（与原文逐字相同），并在 `allow_kana.json` 加**带锚点的
正则**放行其假名；**绝不**新增白名单去掩盖真文本。提取阶段也可以按「与游戏内
真实资源文件同名则跳过」筛选——这是可运行时验证的启发式，不硬编码插件字段。

### 3.5 无假名日文是所有假名门禁的结构性盲区

**现象**：`園田晴香`、`宝来玲緒奈` 整串不含任何假名，只差字形
（`園`、`緒`），库门禁、构建扫描器、执行者自查全部看不见。这是纯汉字日语
（专名、UI 词、菜单词）的固有漏洞，任何基于假名的检查都无效。

**判据**：构建扫描器在插件部分除假名清单外，另出 **kana-free CJK 待复核
清单**（`REVIEW` 行，只报不算失败），并把 JSON-in-JSON 参数拆成真叶子
（共享 `plugin_json_leaves.iter_string_leaves`，否则 2 KB 的 blob 被截成
60 字，什么也看不到）。反向验证：把修复前的 `plugins.js` 喂给新扫描器，三条
全部命中（177 条待复核）。

**处置**：验收必须真读这个清单并对照 `decisions.md` 的人名表。

## 4. 验收：门禁看不见的缺陷与普查

### 4.1 四类盲区

五道门禁能挡住结构性损坏，**语义与一致性上的错它全部放行**。下列四类都是
「每个值都是合法中文、门禁全绿」的缺陷，新游戏收尾时把这四类普查当例行长跑。

1. **identity 值（译文等于原文）**。抓法与复核清单见 §2.7。
2. **跳句专有名词漂移**。同一日文专名在不同句子里被译成多种写法（拉丁缩写、
   音译、意译混用），而每个值都是合法中文，同名不同句的一致性检查拦不到。
3. **JSON 参数里的结构叶子**。结构同构门禁只比**容器**（string 叶子自由，
   因为叶子通常就是译文），所以 `{"label":"…","switchId":"0"}` 里 `switchId`
   被改动不会报错。独立检查：两侧都能当 JSON 解析时，**不含假名与汉字的
   字符串叶子必须逐字节相同**（实测全库 0 违规才算过）。
4. **机翻丢内容**。只看「错」不看「少」：同长度量中文与日文的 CJK 字符数，
   长句（日文 8～14 字以上）比值低于 1.0 的就是疑点。实测健康区间
   ≥ 0.93，掉到 0.6 左右通常是一整句被吐掉。

### 4.2 专名普查的两种做法

- **规范译名 miss 率**：对已定名的专名（人名、地名、物品、货币）取所有含它
  的键，统计有多少值的译文**不含规范译名**，逐条打印。
- **片假名位置对齐普查**（挖没登过的名）：对每个出现 ≥ 6 次的片假名专名，
  在每个句子里取译文**相对位置最接近**的 CJK 或拉丁 token，做众数——第一名
  是该名的常规写法，第二三名就是漂移。位置启发式只作筛选，候选必须整条打印
  给人读。
- 两者都要**防子串误报**：一个以某假名结尾的词会把名字普查引到所有含它的
  句子；前缀式名字会把它包含的另一个名字全部误判；中文同理
  （`层选择地图` 会命中 `楼层选择地图`）。普查脚本必须显式排除。
- 修漂移重名：先修**多数派**，再把普查**重跑在已改过的库上**——第二波才能
  露出尾巴（拉丁缩写、异体字、错字变体）。每轮都要用脚本算出 id 范围，手写
  id 列表必错。

### 4.3 机翻在「人」上的几类错（抽样高频命中）

- **货币与单位现实化**：本地货币被译成现实货币单位。
- **专名被当普通名词**：人名被当成同音词的意译（尤其变量、开关、道具名这类
  非对话文本），一个名字能被拆成完全不同的词。
- **男性角色拿到女性自称**：中文自称有性别指向，机翻会按「说话温柔」错推
  性别。判前先看 `speaker` 或事件里的说话人。
- **成人场景的称谓与代词错位**：主语宾语倒置（「我还硬着」其实是对方被告知），
  敬称被换成第一人称而**丢了名字**（读者不知道是谁）。
- **标点风格**：机器输出会混用「，」与「、」甚至连用（`，、`）；一句原文里
  两种标点并列时，全库扫一遍。

### 4.4 语气与声线

- 中文第一人称不分性别，所以「自称男性代词」**结构上无法直译**：声线靠
  **白话域**承载（短句、命令形、粗词、不用软化尾音）。
- 唯一必须显式处理的是**拿自称开玩笑的台词**（原文自己引用了那个代词）——
  把被引用的代词译成中文里标志性的男性自称，并整库扫它的邻句，保证别处没有
  把同一个词当普通名词意译。
- **禁止娇态词**：中文的女性娇态第一人称会把粗口角色直接变成 OOC。日文
  `人の〜`（＝他人、我）是最容易中招的句式，机翻会一律套上那个娇态词。
- 豪语自称（原文的「〜様」式自指）可用女性豪语（本小姐、老娘），不用男性
  豪语，两者气质不同，选错同样是 OOC。
- 不要整库给角色台词加软化尾音（`～`、啊、呢、啦），只在原文本身有同样符号时
  保留。

### 4.5 普查与改库的操作顺序

1. 先把译文库与键表**快照**到临时目录（单写者可能正在 `append`，直接读会读
   到半文件）。
2. 要改就**先在副本上**用 `apply_rewrites` 模拟，重跑五道门禁加 §4.1 的四类
   普查，全绿再对真库落盘。`apply_rewrites` 是整文件重写，与单写者的
   `append` 并发会互相覆盖。
3. 规则文件的可重跑性：生成器幂等（已存在的 `(old,new,ids)` 不重复追加），
   所以「先空跑看影响面、后正式跑」是同一个脚本。

### 4.6 构建扫描的跳过清单要逐条核实

**现象**：烘焙后残留扫描的跳过清单若靠猜，非文本命令会大量误报（实测某构建
多报约 2.8 万条噪声），清单也可能漏掉真正要提取的字段；反过来，
`tools/qc_build_kana.py` 原先把三类「引擎根本不读的串」报成 unexpected，MZ
游戏因此永远 REVIEW NEEDED（一个失去意义的门禁）：`357` 插件命令的
`parameters[0]` 与 `[1]`（引擎按 `pluginName:commandName` 查处理器）以及
`[2]`（编辑器 `@text` 标签，`command357` 只传 `[3]`）；地图**事件名**
（提取器有意不抽取，有 `findEventByName`、`<namePop:>`、`<TE:>` 的构建在报告
里单独 WARN 供复核）；`System.json` 的资源字段（`sounds[].name`、
`title1Name`…，逐个能在 `audio/` 或 `img/` 里找到同名文件）。

**判据**：在真实数据上迭代到「非文本命令零假阳性」才算可用；校准后残留
61,252 条全为真文本。已核实的类别（MZ，均查过 `rmmz_objects.js`）：`657`
插件命令参数回显（引擎读 `357` 的结构化参数，不读回显）、205
`forceMoveRoute(params[1])` 路线脚本与其 `505` 回显、`118`/`119` 标签名
（跳转按名精确查找，译了会断）、`231`/`241`/`245`/`249`/`250` 音画资源名、
`284 changeParallax(params[0])` 远景图文件名、Actors 的
`characterName`/`faceName`/`battlerName`。

**处置**：这一层是「提取器漏字段」的唯一捉虫点（见 §1.1），所以跳过清单与
提取器是同一份口径（见 §1.2），扫描器要**打印**被排除的类别与数量，而不是
静默 PASS。实测 MZ 的 unexpected 从 3114 降到 0。

### 4.7 提取器与键表必须同一版本

**现象**：`prepare` 之后仓库若被并行会话改了 `translation/mvkeys.py`
（例如新增「`657` 续行与 `357` `@text` 编辑器文本不提取」），而 `prepare`
跑在旧代码上，键表会多出上万条编辑器专用键（实测 86,855 → 52,426，估值
122 块 → 75.9 块）。

**判据**：重跑 `prepare` 后必须核对键数与种类分布。

**处置**：体量协商与分块都以重跑后的键表为准。

## 5. 分块批次

MZ/MV 的翻译走 `docs/translation.md` 的 v2（单写者加文件信箱），下面的分块
工具链服务于非 MZ 引擎与需要分发给多个执行者的批次。

### 5.1 字典收割与预填

- **收割规模**：MTool 运行时字典不可静态烘焙（键是 `\n` 拼接的整条消息加片段
  键，静态匹配会毁句子、漏菜单帮助文本）。实测一款 repack：14,092 个模板键
  → 8,402 预填（exact 3427、strip 1366、drop-name 2937、fragment 672）；
  剩余补翻模板是**逐行片段粒度**（13,589 键、63.8 万字符）。
- **补翻批量**：残留量与预填量决定批次大小。实测两款部分汉化的 MV repack
  各只有一块（453 键／7.8 千字符，650 键／8 千字符），一款自带 1,032 键的
  MTool 字典、其中 354 键命中残留模板（走 `--prefilled`，余下约 99 键交执行
  者），补翻余量用一两个执行者一次跑完即可。`extract_remaining_text.py` 是
  唯一可靠的量尺。
- **`is_name_line` 的部分块值**：`split_block` 的 `is_name_line` 曾把任何不带
  「」的首行当人名行，于是 2,187 个预填块值保留日文首行（「drop-name」，名字
  行没译）。60% 的烘焙把这些部分值写进构建，`extract_remaining_text` 正好把
  那些行当片段抓出。修复是机械的：**从字典丢部分块键，改发逐行片段条目**
  （块值第 1 行起；第 0 行已由 chunks 覆盖）。2,187 全修，0 丢 line0。同时
  `CODE_RE` 改为完整剥离多字母码（`\FX[F]\FFFFF[1000Kenji_0004]`），匹配
  MTool 剥离显示的字典键。
- **identity 条目 SHADOW 逐行 fallback**：见 §2.7。

### 5.2 块尺寸与上下文估算

- **块尺寸二分搜索**：先确定性量 `context.md` 尺寸（12,000 字符 → 90 KB 以上
  的上下文，超预算；11,000 → `--window 1` 下最大约 92 KB），再做执行者探针：
  8,000（2/2 首试）、10,000（2/2）、11,000（3/4，同会话恢复后 4/4）、
  12,000（1/2）。**选 11,000 字符加 `--window 1` → 55 块**（默认 4,500 下是
  142 块）。密集块（90 KB 以上上下文）是 flaky 的，总是 no-file 失败。长
  控制码行（`\FX[F]\FFFFF[1000Kenji_0004]` 前缀）会让上下文预算按字符更吃紧。
  `gen_translation_shards.py` 的 auto 选档已是默认（`--target-chunks N` 加
  `--context-budget-kb 90` 二分搜索，上下文估算误差 < 3%）。
- **估算器的三处 bug（已修加单测）**：`[K]` 行打印含真实换行的键时展开成多
  物理行，`context.md` 实测为估算的 2.3 倍——修复是 transcript 输出一律把 `\n`
  转义成字面 `\\n`；估算按 Python 字符数而预算阈值是文件字节数，日文内容的
  UTF-8 字节是字符数的 2～2.5 倍（90 KB 预算下实测 219 KB）——修复为按 UTF-8
  字节计；估算按字符切全局键而实际写入按键数（600）切，巨型插件键会把首块撑
  到 294 KB——修复为镜像写入器的按键数切分。三处修完后 auto sizing 从
  「20 块 220 KB」变为诚实的「40 块 ≤93 KB」。
- **判据**：新的工具修完必须在本游戏数据上跑一遍验证「估算等于实际」，再启动
  执行者；「误差 < 3%」的说法只在短键游戏上成立。

### 5.3 分块工具的静默缺陷

这些都属于「不报错但结果错」的类型，修完都补了单测。

- **`357` 命令的消息正文不在全量提取范围**：Money Get!、Item Get! 等弹窗正文
  在 `357` 命令的 `parameters[3].message` 字典与 `122`/`355` 脚本字符串里，
  `build_translation.py` 不提取，第一遍烘焙后残留约 789 条。用
  `tools/extract_remaining_text.py` 补翻（约 311 键、5 块），覆盖率从 93.9%
  升到 99.7%。顺序：全量烘焙 → 补翻 → 合并字典 → 在**原始构建**上重烘焙
  （不要在已烘焙目录上叠加）。
- **只有控制码的字典键不能当「剥码匹配」的来源**：`harvest_translation.py`
  用 `strip_codes(key)` 建反向索引，而 `\N[1]` 这类键剥完是空串，于是任何
  「只有控制码」的模板键都会借到它的值（还把开关包两次）。修复：剥完为空
  （或本来就是空）的条目不入索引，这类键归入 missing。
- **值已自带控制码时不要再用键的码包裹**：字典的值常自带 `\C[3]`，再前置或
  后置键的前导尾随码就成了 `\C[3]\C[3]…`，且会被 QC 判为控制码差异。修复：
  值里已出现控制码就原样采用。
- **引号内文本路径丢码**：键 `"\C[3]こんにちは"` 走「引号内匹配」时，重建的
  值只有引号、丢了引号内的 `\C[3]`，出货就是丢样式码的文本。修复：与单行路径
  一致地补回引号内的前导尾随码。
- **`note` 前缀重复**：`<SG説明` 之前的字面前缀本身已含前导码，旧代码又拼了
  一次 `leading_codes(k[:i])`，得到 `\C[3]\C[3]…`。修复：只保留字面前缀。
- **分块 QC 的 KEY ORDER 检查曾是死代码**：`order_diff` 只在键集合不等时才有
  值，而那种情况已由 missing/extra 报告覆盖，于是「键全在但顺序全乱」被静默
  放过。修复：比较两侧共享键的**位置序**，报出第一处错位。
- **补键报告被丢弃**：`issues` 在 `patch_altered_keys` 之后被 `validate` 的
  返回值直接覆盖，「修好了 N 个键」永不打印，修过的块看起来是干净的。修复：
  两份报告合并输出。
- **补翻块生成器里的死代码**：「贪心装包后再合并相邻小块」永远不会触发
  （非末块已是极大的）。删除，并用不变量测试
  （`test_no_chunk_may_be_extended`）钉住「块已极大」。
- **一处误读的纠正**：`chunk_NN.meta.json` 的 `maps` 取自 `where`（人类可读
  位置串 `"<地图名> / EV%03d <事件名>"`，DB 键则是文件名），所以取第一个 `/`
  之前的部分正是**地图名**；不要拿 `loc`（`file#ev0#pg0#c0`）去印证它。

### 5.4 输出卫生与提示词契约

- **写盘前必须做值卫生修复遍历**（mandatory）：折叠被转义的控制码
  （`\\C[27]`）；剥离 `【?...】` 不确定标注；检查控制码 token 序列在键值两侧
  是否一致（缺 `\C` 对是外观性的默认色，保留）；盯重度损坏键上的幻觉值
  （2102 条里有 2 个完全离题），目检码不匹配列表。**任何值修复后，构建里仍是
  旧值，按键匹配的补丁不会重新生效**：要用「旧值到新值」的映射反向补。
- **键与值行数归一化**：值行数归一化到键（补 `""`）；合并并断言每个模板键都
  在；执行者偶尔改键（丢字符、键内出现译词）时按编辑距离 ≤ 3 补到最近的多余
  键。
- **提示词契约（先写后润色）**：114 个硬键块用「读 → 翻 → 最后写」的提示词
  连续失败 3 次（执行者烧光思考预算、文件从未写出）。改为：读规则一次、读块键
  一次；**立即**写 `chunk_NN.zh.txt` 第一遍（拿不准就写最佳猜测加 `【?】`）；
  读回后再写一次改进；最终回复只报路径与条目数。契约是「文件存在前绝不结束，
  先写后润色」，16 块验证 14 块首试通过、2 块可恢复格式滑落。滑动有两种：
  `===KEY===` 分隔符丢失（120 行仍与键 1:1，按行重建 plain 即可）与多行键里
  的字面 `\n` 被写成真实换行。
- **手工兜底**：执行者在同一块反复失败时可以手工翻译（3,000 字符块可行），用
  脚本生成 plain 文件——脚本为每个键前置字节精确的前导空白，因为没有执行者能
  可靠复现 `\u3000` 缩进。
- **术语与消歧**：启动执行者前必须对照烘焙字典查术语（词表猜的角色名读法与
  烘焙字典、游戏内标题可能各不相同）；先 grep 根翻译 JSON 找每个角色名。
  成人姿势与表情类动画标签的消歧依据是事件正文（跑哪些图）与同族标签（表情类
  等于表情），不要从无上下文的假名猜；无法确定就保留构建里的假名（姿势名在
  编辑器不可见）并记入待核清单。
- **跨块术语一致性**：维护 `terms.json` 日志，每个执行者汇报决策，之后每个
  提示词带上累积日志；每个提示词强制确认过的角色词表；尽早发现人名变体
  （全名对简称）并加入。
- **语气要求写进每个块的上下文**：成人场景遵循已认可的语气（词表与语气草案
  留本地，见 `docs/reference/local-layout.md` §8）；剧情与揭示保持悬念；一行
  会溢出消息窗口时用紧凑措辞。

### 5.5 残留检测与豁免

- **用假名量残留，不用字典查**：烘焙后的构建是中文，拿日文字典对照会报
  「100% missing」，没有意义。正确的检测器是在**最终**构建的文本位置上跑假名
  正则：两个类是 `translation/codes.py` 的 `KANA_RE`（判断「是不是文本」）与
  `KANA_LETTERS_RE`（判断「还算不算日文」，判定用后者），并把假名标点
  （`ー`、`・`、`ｰ`、`゛`、`゜`）从计数排除；拟声词里风格保留的小 `tsu` 与
  `ya`、`ちゃん`、`ん` 后缀、`っ`、`ぁ`、`ぃ` 都是可接受的中文游戏风格。
- **顶层列表必须走事件 walker**：`CommonEvents.json` 是**顶层 LIST**，只在
  「带 `events` 的 dict」上分支的文本源 walker 会静默漏掉它全部对话——
  第一次报 166 行残留，真实是 1,851 行（约 3.3 万字符）。修复：元素带 `list`
  键的顶层列表在 DB walker 之前走事件 walker。任何补丁后都要重跑检测器并 diff
  计数。
- **`clean_kana_ticks.py` 对日文文本有破坏性**（词中 `ん`→`嗯`、`ッ`→`!`）：
  只能跑在「中文带尾缀残留」的值上；chunk 输出与 prefill 分开跑，加
  `kind != plugin`、`v != k`、`様` 值守护，绝不跑含真日文片段的值（那要真
  翻译，不是字符替换）。它还会弄坏功能性插件参数字符串（`kind=plugin`），
  总是跳过。
- **题材术语与豁免**：成人题材的主动与被动类词按统一术语表处理，执行者会把这
  类词整串留在译文里（视为专名），QC 假名残留检测会抓到，用 `--sweep` 或修复
  遍历统一，而不是依赖执行者。谜题暗号词（变位词谜题的假名答案）译了会破坏
  谜题，插件 `note` 功能标签（`<モーション変更:guard>` 一类）是功能引用不是
  显示文本——两者都记入该游戏的**本地工作区豁免清单**（位置见
  `docs/reference/local-layout.md`），QC 接受残留。
- **双反斜杠告警要逐条看**：插件参数 JSON 值里键本身含 `\\C[16]`（字面转义
  控制码）时，值保持一致就是正确，不是污染。
- **残留验收口径**：某次大 MZ harvest 的剩余 21 键全属豁免（7 个 CV 或画师
  `様` 名、4 个纯呻吟行、9 个功能性插件字符串、1 个编辑器内部标签）；两款部分
  汉化 MV repack 的残留假名行里除豁免外全是题材术语串，机械替换两个术语后
  清零。

## 6. 字体

### 6.1 MV 的字体回退不等于 `css/game.css`

**现象**：MV 加载 `fonts/gamefont.css`，而只给 MZ 用的
`add_cjk_font_fallback` 改的是 `css/game.css`，简体中文渲染成方块。

**判据**：检查游戏是 MZ 还是 MV 布局（MV 是 `www/` 部署），再看它加载哪个
CSS 文件。

**处置**：用 `add_mv_cjk_font(root, --cjk-font)` 打包 CJK 字体并按
`unicode-range` 拆 `gamefont.css`：假名与 ASCII 指向原字体，汉字指向打包字体。
默认拆分为：假名与日文标点走 `--jp-font`（解析顺序见
`docs/reference/local-layout.md` §5：环境变量 → 本地字体策略 → 打包字体自动
发现；未配置则回退游戏原字体），汉字与拉丁走 `--cjk-font`。

```css
@font-face { font-family: GameFont; src: url("ラノベPOP.ttf");
    unicode-range: U+0020-00FF, U+3040-30FF; }
@font-face { font-family: GameFont; src: url("NotoSansSC.ttf");
    unicode-range: U+3000-303F, U+4E00-9FFF, U+F900-FAFF, U+FF00-FFEF, U+20000-2FA1F; }
```

字体本身不到位时中文会渲染成方块，所以汉化构建必须打包 CJK 字体；`System.json`
的 `gameTitle` 为空时设为官方名。

### 6.2 字体策略必须能在构建里回读确认

**现象**：本地字体表缺失（或字体资产被替换）时，构建可能被当成已经应用了
统一字体，实际中文落在系统回退字体上，字形不统一。

**判据**：策略有三种取值。`required` 解析不到字体即失败，`auto` 只报告不写，
`preserve` 保持游戏原字体。MZ 的 unicode-range 拆分会在 `css/game.css` 写入
标记注释并清空 `mainFontFilename`，据此可回读确认拆分确实落盘；字体资产的
sha256 与 manifest 不符时报 `checksum mismatch` 并拒绝应用。

**处置**：汉化构建用 `required` 跑烘焙，缺字体时按 WARN 报出并说明缺了什么，
不得静默降级；各引擎的改动点见 `docs/reference/local-layout.md` §5。

## 7. 打包

### 7.1 运行时字典不进包

**现象**：构建根目录带着 MTool 的运行时字典（`翻译文件.json` 或根目录
`<title>.json`），打包时难以判断该不该删。

**判据**：它只是构建期的数据源（`resolve_text_keys` 的第 2、3 级来源），
禁用插件后游戏零引用，不是游戏资源。`clean` 只认根目录 `<title>.json` 这个
名字，而且烘焙会从源副本把它复制回来。

**处置**：删除必须放在 **烘焙之后、打包之前**。更省事的做法是把补译完成的
中文写回游戏自带表格的 `cn` 列：表格是随包资源，下一次烘焙直接用它。

### 7.2 根目录的奖励 ZIP 不是垃圾

**判据**：删除前先确认它是不是游戏的官方通关特典——游戏内 NPC 会经
`<namePop:…>` `note` 引用它。

**处置**：确属特典就保留，并把对应地图里的名字引用补成译名。

### 7.3 译库随包归档

烘焙自动把译库写为构建根目录的 `translation_kv.json`（`--no-kv` 关闭），
便于日后修改与重译，打包时随包归档。名字引用（`<namePop:…>`）在对应地图里
补成译名并记入该文件，`namePop Lv<N>` 标签保持原样。
