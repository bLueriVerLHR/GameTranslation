## 1. 翻译（zh_CN 翻译文件.json）

- 用 `tools/translate_rpgmaker.py <src> <out> --trs 翻译文件.json`，或用其
  `translate_data` 直接烘焙进构建（只数据文件；JSON 写 `indent=2`、
  `ensure_ascii=False`、无 BOM）。
- 翻译后**打包 CJK 字体**，否则中文渲染方块。最佳做法：加
  `NotoSansSC.ttf`（OFL，google/fonts GitHub），按 `unicode-range` 拆
  `fonts/gamefont.css`，假名/ASCII 保留原字体、汉字用 Noto：
  ```css
  @font-face { font-family: GameFont; src: url("ラノベPOP.ttf");
      unicode-range: U+0020-00FF, U+3040-30FF; }
  @font-face { font-family: GameFont; src: url("NotoSansSC.ttf");
      unicode-range: U+3000-303F, U+4E00-9FFF, U+F900-FAFF, U+FF00-FFEF, U+20000-2FA1F; }
  ```
- `System.json.gameTitle` 为空时设官方名。

### 1.1 ExternMessage.js 游戏（MV）

- **对话在 `data/ExternMessage.csv`，不在 JSON。** 有些 MV 游戏带
  UTF-16LE `ExternMessage.csv`（列 `名前(ID),本文(body),...`）；事件只含
  指向它的 `\M[ID]` 引用。`translate_rpgmaker.py` 原本只烘焙 `data/*.json`
  → 开场场景保持日文，且贪心翻译器重写了 `\M[...]` 里的 ID，破坏 CSV
  查找。**修复（已应用于 `tools/translate_rpgmaker.py`）：** (1)
  `translate_text` 现在保护控制码括号（`\M[ID]`、`\V[1]`、`:name[...]`、
  …）— 只翻译它们之间的纯日文片段，`:name[NAME,FACE]` 的 NAME 部分除外
  （它是显示文本；已验证无 `:name` 参数与 CSV id 冲突）；(2) 新
  `translate_extern_csv` 逐行翻译 本文 列，ID 保持不动、保留
  UTF-16LE/BOM（或 utf-8-sig/cp932）+ CRLF。这类修复后从源重跑整条
  流水线 — 旧构建的 `\M[...]` 引用已损坏。
- **MV 字体回退 ≠ `css/game.css`。** MV 加载 `fonts/gamefont.css`；
  `add_cjk_font_fallback`（仅 MZ）没用，简体中文渲染方块。
  `add_mv_cjk_font(root, --cjk-font)` 打包 CJK ttf 并按 `unicode-range`
  拆 `gamefont.css`（假名/ASCII → 原字体，汉字 → 打包字体）。
  **2026-08 后默认拆分为**：假名/日文标点 → `--jp-font`（解析顺序：
  `JP_FONT_PATH` → `docs/table/local_font_path.txt` 第二行 → 自动发现
  `docs/table/fonts/`，未配置则回退游戏原字体），汉字/拉丁 → `--cjk-font`。
- **翻译后验证 CSV ID：** 地图 JSON 里每个 `\M[ID]` 必须在 CSV 的 名前
  列存在（排除既有缺失如 `\V[320`、`テスト`、单假名 — 源里本来就没有）。

### 1.2 MTool repack 可能带未翻译 `data/` + 根 `<title>.json`

一款 repack 正常 — 数据已翻译；另一款不是：repack 在游戏根带 MTool
字典、*数据文件仍是日文*；你必须自己烘焙：
`python tools\translate_rpgmaker.py <built> <out> --trs "<title>.json"`
（那次 7742 条）。它还向 `css/game.css` 追加 CJK 字体回退。之后重
verify + serve --test。别假设"repack = 已烘焙"。

## 2. 静态 subagent 翻译工作流（全量批次）

- **MTool 运行时字典不可静态烘焙。** 一款游戏带根 `<title>.json`
  （10,191 键），键是 `\n` 拼接的整条消息（引擎显示时重组）+ 片段键。
  静态烘焙（旧贪心回退）毁句子、菜单帮助文本没翻。修复是静态工作流 —
  `build_translation.py`（提取、块合并模板）→ `glossary.json` →
  `gen_translation_shards.py` → subagent → `bake_translation.py`
  （只精确匹配）。完整指南 `docs/translation.md`。
- **消息块修多行上下文。** 连续 `401`/`405` 命令是一条消息：`\n` 拼成
  单翻译键，烘焙器拼接同一段、按命令拆回值（短值 `""` 行补齐；多余行
  追加命令）。
- **流程已换代**：MZ/MV 走 `docs/translation.md` 的 **v2**（单译者 + 文件
  信箱 + 五道门禁）。本节以下的块尺寸/额度/分批追加经验属于 **v1 切块流程**
  （已退役；chunk 工具仍服务非 MZ 引擎）——只作历史教训参考，不再作为流程。
- **LLM 输出卫生：** (1) 修复遍历：双重转义非法转义、转义游离引号；
  (2) agent 偶尔改键（丢字符、键内译词）— 按编辑距离 ≤3 补到最近的多余
  键；(3) 值行数归一化到键（补 `""`）；(4) 合并并断言每个模板键都在。
- **跨分块术语一致性：** 维护 `terms.json` 日志；每个 agent 汇报决策，
  之后每个 prompt 带上累积日志。每个 prompt 强制确认过的角色词表；尽早
  发现人名变体（全名 vs 简称）并加入。
- **游戏 owner 语气指令进每个 chunk 上下文：** 成人场景遵循 owner 认可
  的语气（词表留本地，见 `docs/translation.md` §6）；剧情/揭示保持悬念；
  一行会溢出消息窗口时紧凑措辞。

## 2c. 「100% 覆盖」不等于译完（2026-09 实战教训，mandatory）

一款游戏 v2 全量跑完、五道门禁全绿（`coverage 0 missing`），把构建拿去浏览器实测
时，**说话人名栏仍是日文**（`豊聡耳神子`）。原因不是翻译质量，而是**提取器覆盖
不全**：`101` 的 `parameters[4]`（名牌）从未进入 `keys.jsonl`，“100%” 只是对**已提取
子集**的 100%。扩展提取器后重跑，**又补出 13,321 键**（名牌 10,296 / `657` 续行
1,964 / `402` 分支标签 451 / `357` 插件文本 404 / DB 206）。

教训与做法：

- **验收硬指标是「最终构建里没有日文」，不是 gates 绿。** 收尾必须在**烘焙后的构建**
  上扫描 `data/*.json` 的每个字符串（不只提取路径），用**假名字母类**
  `[\u3041-\u3096\u30a1-\u30fa\uff66-\uff9d]`（`・`(U+30FB)/`ー`(U+30FC) 是符卡
  中点与长音符，属允许项；当初把它们算作假名导致 4,429 条假阳性）。
- **重提取必须从日文原始数据做**，不能从已烘焙的中文构建做：已翻译的句子可能不再含
  假名/汉字（纯 `——`、`……!`），提取器会当非文本丢掉 id（实测掉了 23 个 id）。
  重提取要断言「id 只增不减」：旧 id 集 ⊆ 新 id 集。
- **新类别能大幅机械预填**：同日语原文已在库里译过 → 直接复用（本次 6,983 条：名牌
  6,532 + 分支标签 451）；`402` 分支标签应与同组 `102` 选项译文逐字一致（按选项索引
  结构配对）。预填仍走 `append` 提交（控制码校验兼做正确性检查）。
- 插件指令（`357`/`657`）的参数是**标识符 + 散文**混合：插件名/命令名/JSON 参数对象/
  路径/脚本片段绝不能译；只有读出是散文的字符串才进 `keys.jsonl`。
- DB 战斗台词（`message1`/`message2`）含 `%1`/`%2` 占位符，必须逐字保留。
- **第二轮重提取又拖出两处**（同一款游戏，修完第一轮后再次在烘焦后构建上扫残留才
  发现）：① 插件指令参数**对象内部**的字段（`{"messageText": "叫び声が響く……"}`
  弹窗文本、`{"text": "Shift 键快进"}` 界面提示）——只看顶层字符串会全漏；
  ② **整行半宽片假名**（`ﾌﾞﾂﾌﾞﾂ……`）——假名类不含半宽块时被当「无假名」非文本丢弃。
  所以残留扫描的假名类要与提取器**同一个定义**（`translation/codes.py` 的 `KANA_RE`），
  并把残留分成「有意跳过的内部字段」与「意外残留」两类——后者非零就是真缺口；
  该脚本以退出码表达结论，可当门禁跑。
- **「有意跳过」清单本身就是风险源：每一类都要到插件代码里核实（第三轮教训）。**
  同一款游戏交付后复核时发现：被归为「编辑器内部名、跳过」的 `System.json`
  `switches`/`variables` **名字**，被变量窗口插件 `drawText($dataSystem.variables[id])`
  画在界面上——是玩家能看到的日文。核实方法（可复用）：在成品 `js/`（含插件）里
  搜索该字段的读取模式（`MapInfos` / `CommonEvents[..].name` / `$dataSystem.variables`），
  命中的再读上下文看是 `drawText`/赋值到可见对象，还是仅按 id 取数据。
  结论：`MapInfos`/`CommonEvents`/`Tilesets` 的 `name` 在实测构建中**无任何插件读取**
  （确为内部名），而 `switches`/`variables` 名字**要提取**（引用一律走 id，全库无
  按名查找，译名安全）。残留扫描脚本的跳过清单必须随提取器同步收紧——否则
  “0 意外残留”会是假阴性。

## 3. 残留翻译批次（v1 时代的历史记录）

> **历史提醒**：本节写于 v1 切块/write-first 时代。当前 MZ 流程是
> `docs/translation.md` 的 **v2**（单译者 + 文件信箱 + 五道门禁）。本节只
> 保留那一次会话的 **教训**（假名残留检测、CommonEvents 顶层列表、值卫生
> 修复），这些仍然有效。

这次会话用 16 块 subagent 批次（补 2102 键）翻译了 AI 字典烘焙构建里的
残留日文。三个硬教训：

- **用假名量残留，不用字典查。** 烘焙后构建是中文；对照日文字典报
  "100% missing" 无意义。正确残留检测器是**最终**构建文本位置上跑假名
  正则（`[\u3040-\u30ff]`）。同时把假名标点从计数排除（`ー・゛゜` 与
  拟声词里风格保留的小 tsu/ya 类助词没问题；`ちゃん`/`ん` 后缀与
  `っ`/`ぁ`/`ぃ` 是可接受的中文游戏风格）。
- **CommonEvents.json 是顶层 LIST — 只在"dict with `events`"上分支的
  文本源 walker 会静默漏掉它全部对话。** 第一次报 166 行残留；真实
  1851（~33k 字符）。修复：元素带 `list` 键的顶层列表在 db walker 之前
  走事件 walker。任何补丁后总重跑检测器并 diff 计数。
- **修 subagent "思考模式死亡"的修复真有效 — 先写。** 114 个硬键块用旧
  "读 → 翻 → 最后写" prompt 失败 3 次（agent 烧光思考预算、无文件结束）。
  新 prompt 契约，16 块验证（14 首试 OK，2 个可恢复格式滑落）：
  1. 读规则一次，读块键一次。
  2. **立即**写 `chunk_NN.zh.txt` 第一遍（拿不准：最佳猜测 + `【?】`）。
  3. 读回，再 Write 一次改进。
  4. 最终回复 = 路径 + 条目数。
  "文件存在前绝不结束。先写，后润色。"（此契约下块可以很大 — 约
  9k-11k 字符 — v1 切块契约，已退役。）两个格式滑落：`===KEY===` 分隔符丢
  （120 行仍与键 1:1 → 按行重建 plain）和一个多行键里字面 `\n` 文本写成
  真实换行。
- **补丁前 agent 值卫生修复遍历（mandatory）：** (1) agent 转义控制码
  （`\\C[27]`）— 折叠双反斜杠；(2) 剥离 `【?...】` 不确定标注；(3) 检查
  控制码 token 序列键值两侧；缺 `\C` 对是外观性的（默认色），保留；
  (4) 盯重度损坏键上的幻觉值（2102 里有 2 个完全离题）— 目检码不匹配
  列表。**任何值修复后，构建里是旧值，按键匹配的补丁不会重新生效：
  用 旧→新 值映射反向补。**
- **启动 agent 前必须对照烘焙字典查术语**（第一次词表猜了角色名一个
  读法；烘焙 AI 字典用另一个，游戏内标题第三个）。先 grep 根翻译 JSON
  找每个角色名。
- **姿势/动画名消歧：** 对成人姿势/表情类动画标签（技术消歧样例），作者
  意图在事件正文（跑哪些图）与同族其他标签（表情类 = 表情）之间。别从
  无上下文假名猜；无法确定就保留构建里的假名（姿势名编辑器不可见）并向
  用户标记。
- **手工兜底：** subagent 在同一块反复死亡时，编排者可以手工翻（3k
  字符块完全可行），用脚本生成 plain 文件 — 脚本为每个键前置字节精确的
  前导空白；没有 agent 能可靠复现 `\u3000` 缩进。

### 3.1 TemplateEvent `<TE:name>` note 引用 vs 已译事件名

症状：翻译构建启动、地图渲染，但**玩家永远无法移动**。`canMove()` 保持
false，因为 `$gameMap.isEventRunning()` 恒 true；地图解释器空闲
（`running=false`、`index 0/0`），但 `isAnyEventStarting` 为 true，事件 1
每帧卡在 `_starting=true`。

根因：**TemplateEvent.js** 把 Note 含 `<TE:name>` 的事件替换成模板事件，
在模板地图（插件参数 `TemplateMapId`）里**按名查找**：

    generateTemplateId: templateId = findMetaValue(event, 'TE')
        -> searchDataItem($dataTemplateEvents, 'name', templateId)

模板地图持有短"setup-and-erase"模板列表（5 条命令 vs 原 23 条）。翻译
把模板地图的事件**名**译成中文，但每个 Note 的 `<TE:マップ初期処理>`
保持原样 → 按名查找失败 → 模板永不应用 → 原无条件 autorun 事件（永不
自我擦除）每帧重触发 → `isEventRunning()` 恒 true → 移动锁死。

诊断路径（已验证）：关键运行时差异不在数据结构或插件文件（除译文字符串
外字节一致），而在**运行时状态** — 对比构建间的
`Game_Event._erased/_starting/_pageIndex`。原版事件 `erased: true`（模板
列表跑完擦除）；翻译构建永远 `erased: false, pageIndex: 0, trigger: 3`。
记录 `interp.setup listLen` / `EVENT.start` / `eraseEvent` 的 trace 插件
显示原版用 `listLen=5`（模板）setup 事件，翻译构建总用 `listLen=23`
（原版）。

修复（已烘焙进 `tools/bake_translation.py`）：翻译事件 Note 里的
`<TE:name>` 引用与事件名同步 — `_translate_note_refs()` 用同一精确匹配
字典改写 `<TE:ja>` → `<TE:zh>`（跳过 `\v[1]` 类控制码引用）。从干净源
副本重烘焙；旧构建上的手工 note 编辑会被之后的烘焙覆盖。

同一会话还修了：`bake_translation.py` 曾以 `encoding="utf-8-sig"`
（写时加 BOM）写所有 `data/*.json` — 全部改为纯 `utf-8`（System.json
里的 BOM 破坏引擎 `JSON.parse`）。

教训：翻译时**扫描插件里按名称查找的模式**（`<TE:`、`@command` 名引用、
`PluginManagerEx.findMetaValue`）— 任何按显示名解析实体的插件（模板
事件、气泡名、`callEventByName`、选择帮助标签）在查找只有一侧被翻译时
坏掉。

## 4. 两款部分汉化 MV repack 的补翻批次（2026-08）

两款 MV `www/` 部署、easy 加密、**部分汉化**的 repack（正文/DB 大部分
已译，System UI/事件名/开关变量/少量对话残留日文）走完整流水线 +
残留补翻。规模极小：每款仅 1 个 chunk（一款 453 键/7.8k 字符，另一款
650 键/8k 字符）— 补翻剩余量可以用 1-2 个 subagent 一次完成，无需
多轮。

- **两款均已汉化但残留形态不同，补翻前先量。** 一款自带 MTool 字典
  （1,032 键，354 命中残留模板 → 直接做 `--prefilled`，剩余 ~99 键
  subagent 译）；另一款是公开汉化版，残留全在 UI/事件名/开关变量。
  `extract_remaining_text.py` 是唯一可靠的量尺。
- **题材术语统一（owner 定案，本地 adult 词表已记录）：** 成人题材的
  主动/被动类词 → 按统一术语表处理。补翻 agent 会把这类词整串留在
  译文里（视为专名），QC 假名残留检测会抓到 — 用 `--sweep` 或修复遍历
  统一，而不是依赖 agent。
- **谜题暗号词豁免：** 一款的 DB description 里有一组假名暗号（变位词
  谜题答案，如 5 个假名词），翻译会破坏谜题 — 记录到
  `docs/table/<Game>/notes.md` 豁免清单，QC 接受残留。
- **插件 note 功能性标签豁免：** `<モーション変更:guard>` 类
  `<插件标签>` 是功能引用不是显示文本 — 保留，记入豁免清单。
- **修复遍历：** 残留假名行里除豁免外全是题材术语串 — 机械替换两个
  题材术语后全部清零。double-backslash 告警要逐条看：插件参数
  JSON 值里键本身含 `\\C[16]`（字面转义控制码），值保持一致就是正确，
  不是污染。
- **烘焙覆盖闸门验证：** 两款分别 83.8% / 89.8% 覆盖 — 补翻块小所以
  达标；`--min-coverage` 默认 0.5 没触发。
- **交付：** 两款都无 >4096 PNG（无需缩放），`translation_kv.json`
  已随包归档，压缩包 `7z t` 完整性测试 OK。

## 5. 大型 MZ 插桩游戏的翻译会话（2026-08）

### 5.1 分块工具的估算 bug（已修复 + 单测）

- **多行键膨胀**：`[K]` 行打印含真实换行的键时展开成多物理行，context.md
  实测为估算 2.3 倍。修复：transcript 输出一律把 `\n` 转义为字面 `\\n`
  （与 ja.txt 转义一致，且让估算可精确）。
- **字符 vs 字节**：估算按 Python 字符数，预算阈值是文件字节数 — 日文
  content 的 UTF-8 字节为字符数 2~2.5 倍，90KB 预算下实测 219KB。
  修复：`_chunk_context` 按 UTF-8 字节计。
- **全局块切分不一致**：估算按字符切全局键，实际写入按键数（600）切 —
  巨型插件键会把首块撑到 294KB。修复：估算镜像写入器的按键数切分。
- 三处修复后 auto sizing 从"20 块 220KB"变为诚实的"40 块 ≤93KB"。
- 教训：新的工具修完必须在本游戏数据上跑一遍验证估算==实际，再启动
  subagent；此前"误差 <3%"的说法只在短键游戏上成立。

### 5.2 插件参数巨型 JSON（>300 字符的 kind=plugin 键）

- 18 个键占 20.6 万字符（最大 83KB）：技能动画表、菜单模板等。
  整串翻译不可行 → 从模板剔除，走 `plugin_json_leaves.py`：
  extract（204 叶子）→ 叶子翻译（1 个 subagent）→ rebuild（23 个 blob
  变更）→ `plugin_blobs_translated.json` 后合并覆盖进 translated.json
  （blob 重建必须覆盖模板整串译文）。
- 插件 JSON 的功能键（`位置X`/`テキスト名`/`条件`/`アニメ名` 等）必须
  保持日文；叶子收集只取 VALUE，但最终 kana 残留扫描会报这些"键里的
  假名" — 属正常，勿修。
- 字体名/样本文件名字面值（`07鉄瓶ゴシック.woff`、`サンプル/一言_1`）
  必须进 `--exempt`，否则叶子翻译改坏引用。
- 事件 note 带插件标签（`<BFC_座標:...>`/`<CounterExt:...>`）是功能数据，

### 6.2 harvest / 分块 QC 的几处静默错译源（2026-09，已修复 + 单测）

这一轮给此前 0% 覆盖的分块/收割/QC 工具补了单测，写测试时逐条查出来
的——都属于「不报错但结果错」的类型：

- **只有控制码的字典键不能当“剥码匹配”的来源**：`harvest_translation.py`
  用 `strip_codes(key)` 建反向索引，而 `\N[1]` 这类键剥完是空串 →
  任何“只有控制码”的模板键都会借到它的值（还把开关包两次）。
  修复：剥完为空（或本来就是空）的条目不入索引，这类键归入 missing。
- **值已自带控制码时不要再用键的码包裹**：字典的值常自带 `\C[3]`，
  再前置/后置键的前导/尾随码就成了 `\C[3]\C[3]…`，且会被 QC 判为
  控制码差异。修复：值里已出现控制码就原样采用（不再包裹）。
- **引号内文本路径丢码**：键 `"\C[3]こんにちは"` 走“引号内匹配”时，
  重建的值只有引号、丢了引号内的 `\C[3]`——直接出货就是丢样式码的文本。
  修复：与单行路径一致地补回引号内的前导/尾随码。
- **note 前缀重复**：`<SG説明` 之前的字面前缀本身已含前导码，旧代码
  又拼了一次 `leading_codes(k[:i])` → `\C[3]\C[3]…`。修复：只保留
  字面前缀（它就是原文里那一段）。
- **分块 QC 的 KEY ORDER 检查是死代码**：`order_diff` 只在键集合不等时
  才有值，而那种情况已由 missing/extra 报告覆盖 → “键全在但顺序全乱”
  会被静默放过（ja/zh 契约是逐行的，顺序错位是真的缺陷）。修复：比较
  两侧共享键的**位置序**，报出第一处错位。
- **补键报告被丢弃**：`issues` 在 `patch_altered_keys` 之后被 `validate`
  的返回值直接覆盖，于是“修好了 N 个键”永不打印，修过的块看起来是干净
  的。修复：两份报告合并输出（修好仍然算“有改动”，应当可见）。
- **补翻块生成器里的死代码**：“贪心装包后再合并相邻小块”永远不会触发
  （非末块已是极大的，再加下一个键必然超预算）。删除，并用不变量测试
  （`test_no_chunk_may_be_extended`）钉住“块已极大”，防止回归。

同时纠正一处误读：`chunk_NN.meta.json` 的 `maps` 取自 `where`（人类可读
位置串 `"<地图名> / EV%03d <事件名>"`，DB 键则是文件名），所以取第一个
`/` 之前的部分得到的正是**地图名**；不要拿 `loc`（`file#ev0#pg0#c0`）去
印证它。

## 7. 五门禁看不见的四类缺陷，以及挖出它们的抽样法（2026-09）

v2 的五道硬门禁（覆盖 / 控制码 / 假名 / 换行数 / 待决）能挡住结构性
损坏，但**语义与一致性上的错它全部放行**——下面四类都是「每个值都是
合法中文、门禁全绿」的缺陷，靠对全库做専用普查 + 随机抽样人眼复核才
挖得出来。新游戏收尾时把这四类普查当例行长跑。

### 7.1 四类盲区

1. **identity 值（译文 == 原文）**。假名门禁只抳**带假名**的残留，
   bake 也只剔除（identity + 假名）条目；**纯汉字同形**的值既过门禁
   也不被剔。大部分合法（男/女/魔女/防御/命中率/道具，中日同形），
   但日文専用词会静默留在游戏里。判据是「这个词在中文里也这么写
   吗」，不能改成一条机械规则。
2. **跳句专有名词漂移**。同一 ja 専名在不同句子里被机翻成多种写法
   （拉丁缩写 / 音译 / 意译混用），而每个值都是合法中文——**同名不同
   句**的一致性检查拦不到。两种普查见 §7.2。
3. **JSON 参数里的结构叶子**。结构同构门禁只比**容器**（string 叶子
   自由，因为叶子通常就是译文），所以 `{"label":"…","switchId":"0"}`
   里 switchId 被改动不会报错。独立检查：两侧都能当 JSON 解析时，
   **不含假名/汉字的字符串叶子必须逐字节相同**（实测全库 0 违规才算
   过）。
4. **机翻丢内容**。只看「错」不看「少」：同长度量 zh/ja 的 CJK 字符
   数，长句（ja ≥ 8~14 字）比值 < 1.0 的就是疑点（实测健康区间
   ≥ 0.93，掉到 0.6 左右通常是一整句被吐掉了）。

### 7.2 专有名词普查（两种，互补）

- **规范译名 miss 率**：对已定名的专名（人名/地名/物品/货币）取所有
  含它的键，统计有多少值的译文**不含规范译名**，逐条打印。
- **片假名位置对齐普查**（挖没登过的名）：对每个出现 ≥ 6 次的片假名
  专名，在每个句子里取译文**相对位置最接近**的 CJK/拉丁 token，做众
  数——第一名是该名的常规写法，第二三名就是漂移。位置启发式只是
  筛选，候选必须整条打印给人读。
- 两者都要**防子串误报**（真实踩到过的）：一个以某假名结尾的词会把
  名字普查引到所有含它的句子；前缀式名字会把它包含的另一个名字全部
  误判；中文同理（`层选择地图` 会命中 `楼层选择地图`）。写普查脚本时
  必须显式排除。
- 漂移重名的修法：先修**多数派**，再把普查**重跑在已改过的库上** ——
  第二波才能露出尾巴（拉丁缩写/异体字/错字变体）。每轮都要把
  id 范围算出来而不是手写（手写 id 列表必错）。

### 7.3 机翻在「人」上的几类错（抽样高频命中）

- **货币/单位现实化**：本地货币被译成现实货币单位。
- **専名被当普通名词**：人名被当成同音词的意译（尤其变量/开关/道具名
  这类非对话文本），一个名字能被拆成完全不同的词。
- **男性角色拿到女性自称**：中文自称有性别指向，机翻会按「说话温柔」
  错推性别。判前先看 `speaker` / 事件里的说话人。
- **成人场景的称谓/代词错位**：主语/宾语倒置（「我还硬着」→ 其实是
  对方被告知），敬称被换成第一人称而**丢了名字**（读者就不知道是谁）。
- **标点风格**：机器输出会混用「，」与「、」甚至连用（`，、`）；
  一句原文里两种标点并列时，全库扫一遍。

### 7.4 仆娘/男性化语气角色的中文声线（owner 关注点）

- 中文第一人称不分性别，所以「自称男性代词」这件事**结构上无法直译**：
  声线靠**白话域**承载（短句、命令形、粗词、不用软化尾音）。
- 唯一必须显式处理的是**拿自称开玩笑的台词**（原文自己引用了那个代
  词）——把被引用的代词译成中文里标志性的男性自称，并整库扫它的
  邻句，保证其它地方没有把同一个词当普通名词意译。
- **禁止娇态词**：中文的女性娇态第一人称/自称会把粗口角色直接变成
  OOC。日文 `人の〜`（＝他人/我）是最容易中招的句式——机翻会一律
  套上那个娇态词。
- 豪语自称（原文的「〜様」式自指）可用女性豪语（本小姐/老娘），不
  用男性豪语（二者气质不同，选错同样是 OOC）。
- 不要整库给角色台词加软化尾音（`～`、啊/呢/啦），只在原文本身有同
  样符号时才保留。

### 7.5 验证顺序（脚本化，勿背）

1. 先把库 + keys **快照**到临时目录（单写者可能正在 append，直接读会
   读到半文件）。
2. 要改就**先在副本上** `apply_rewrites` 模拟 + 重跑五门禁 + 跑 §7.1
   的四类普查，全绿再对真库落盘（`apply_rewrites` 是整文件重写，与单
   写者的 append 并发会互相覆盖）。
3. 规则文件的可重跑性：生成器幂等（已存在的 (old,new,ids) 不重复追加），
   所以「先空跑看影响面、后正式跑」是同一个脚本。

### 7.6 同一轮修好的两处烘焙工具缺陷（已加单测）

- **插件参数名不能限定 ASCII**：路径解析器把名字限定为 ASCII 标识符时，
  日文参数名与含空格参数名会抛 ``BakeError``，而它抛在 try/except
  **之外** → 整个烘焙中断（不是跳过）。名字应允许除 `.`/`[`/`]` 之外的
  任何字符，且只能出现在路径开头或 `.` 之后（仍把畸形路径当错）。
- **「是否有字体切换插件」不能对 plugins.js 做全文文本匹配**：`status:
  false` 的条目也被算作启用，于是本可做 CSS `unicode-range` 拆分的构建
  被跳过拆分（假名面从未声明，全部字形回退到同一个中文字面）。改为解
  析 plugins.js 后**只看 status 为真**的条目；文件不可解析时保持保守
  （当作有插件）。拆分的实际形态：汉字面一份 `@font-face`，假名/假名
  标点用 `unicode-range` 指到日文字面。

## 8. note 标签载荷：只翻一边会把道具从菜单里弄没（2026-09 定案）

### 8.1 事故形态

一款 MZ 游戏的道具菜单有个自定义分类页签。插件把页签名放在**插件参数**
（`categoryList`）里，道具则在 `note` 里用 `<itemCategory:…>` 标记自己属于
哪个分类。两者**按名逐字匹配**：

```js
Window_ItemList.prototype.includes = function (item) {
  if (item && item.meta.itemCategory) return this._category === item.meta.itemCategory;
  return _Window_ItemList_includes.call(this, item);
};
```

翻译把插件参数译成了中文（它确实是显示文本），而 `note` 里的标记保持日文
（提取器**有意不碰 note**，因为那里绝大多数是插件命令/内嵌 JSON/查找键）。
结果：`_category`（页签名）与 `item.meta.itemCategory`（日文标签）永不相等，
而这批道具因为带标签又不会落回普通分类——**它们在道具菜单里彻底消失**。
五道门禁全绿（每个值都是合法中文、控制码一致、无假名残留），`verify` 也全绿
（PNG/JSON/音频引用都正常）——启动与文本层面看不出任何异常。

### 8.2 怎么发现的（可复用的手法）

1. **在最终构建上跑假名普查**（`docs/translation.md` 的 mandatory 步骤），
   按 **JSON 路径**分类每一条命中：`parameters[2]`（357 的 @text）、657 回显、
   `MapInfos[].name`、`Animations[].name`、`note` … 绝大多数属于「有意不提取」。
2. 剩下的 `note` 命中里，凡是**载荷是散文**（含假名且不是纯数字/坐标）的，
   逐条问：「这个插件会把它画出来吗？」——去 `js/plugins` 里搜标签名，看
   它把载荷当**标签**（要翻）还是当**键**（不能单边翻）。
3. 只要插件把载荷与**别处的字符串**做比较/查找，就把那个「别处」也搜出来
   （插件参数、事件注释、另一个 note）——**两边必须同译或同不译**。

### 8.3 工具链的修法（已实现 + 单测）

`note` 仍然默认整体不提取（安全默认），改用**显式白名单**打开：

```
python -m translation.cli prepare <game_dir> <work_dir> --note-tags 拡張説明,itemCategory
```

- 白名单**由调用者给出**，工具里不硬编码任何游戏数据（见 AGENTS.md 的
  「工具禁止硬编码游戏专属数据」）。
- 每个标签**每次出现**一个键，id 形如
  `data/Items.json#[12].note#itemCategory[0]`（DB 记录）或
  `data/Map172.json#events[1].note#LB[0]`（地图事件；两类 note 都扫），
  出现序号保证唯一且稳定，同一 note 里重复的标签不会撞键；`ja` 只含**载荷**，
  标签名不进键。
- 载荷不含假名/汉字（纯数字、坐标、布尔）时自动不算文本——那是配置。
- `bake` 只替换**该次出现**的载荷：标签名与同一 note 里的其它标签逐字节
  不动；译文含 `<`/`>` 时**拒写并报 skip**（会破坏标签语法），不静默写坏。
- 与以往相反：**重复烘焙是幂等的**（位置寻址），但 id 漂移（标签被删/挪位）
  必须报 skip，不能猜。
- 提取的标签清单写入 `stats.json` 的 `note_tags`，事后可查「这次打开了哪些」。

### 8.4 把「还有哪些 note 标签在显示」变成普查（而非法猜）

同一款游戏后来靠一份**标签清单普查**又抓到一个：`<LB:名字>`（事件头顶的地图标签）
的载荷是画在事件上方的文字（纯显示、无匹配风险），它住在**地图事件的 note** 里，
不在 DB 记录里——所以提取器要同时扫两处。普查做法：

1. 扫全构建 `data/*.json` 里所有 `<tag:...>`，按标签聚合载荷；
2. 只留下**载荷含假名**的标签（纯数值/坐标自然落选）；
3. 对每个标签去 `js/plugins/` 里找引用它的插件，读它把载荷当**显示文本**还是
   **查找键**（看是否与其它字符串做比较）。

跑完剩下的应为 0；不为 0 的就是下一个 §8.1。

### 8.5 结论

- **插件的「按名匹配」不止发生在插件参数之间，也发生在插件参数与数据文件
  之间。** 翻译前先 `rg` 那个参数值，看它是否又出现在 `data/*.json`（含
  `note`）、事件注释里；出现在哪就必须一起翻。
- 另一类 note 载荷（帮助窗扩展 `<拡張説明:…>`、事件头顶标签 `<LB:…>`）没有
  匹配风险，纯显示文本，同样用这个开关一并解决（同一款游戏实测 18 + 8 处）。
- 「门禁全绿 + verify 全绿」仍然不是交付判据：**必须在最终构建上做假名
  普查+路径分类**，否则这类「菜单里少了一整批东西」的缺陷会静默出货。


## 9. v2 单写者流程 + 烘焙后验收（2026-09，MZ 大插件集）

### 9.1 提取器与 keys.jsonl 的「不同一版本」陷阱

- `prepare` 之后仓库若被并行会话改了 `mvkeys.py`（例：新增「657 续行与 357
  `@text` 编辑器文本不提取」），而 `prepare` 跑在旧代码上，键表会多出上万条
  编辑器专用键（实测 86,855 → 52,426，估值 122 块 → 75.9 块）。**重跑
  `prepare` 后必须核对键数与种类分布**，否则整份体量协商都建立在错数字上。

### 9.2 identity 值是纯汉字日文漏译的唯一藏身处

- 假名字母类门禁与烘焙后残留扫描都查不出**纯汉字**日文（`購買`、`塩味`、
  `価格`）。唯一暴露点是「与原文逐字相同（`value == key`）」的条目：逐条过目
  identity 清单（实测单轮只有 11 个 distinct 值，人工可过）。共享字形人名
  （`根岸里美`）合法存在，所以这是**复核清单而非失败判定**。
- 清单的过滤条件要写对：含 ASCII 的分支标签
  （`en(v[12]>=1)根岸里美　if(!s[222])`）与含假名的串都不该进清单，否则
  淹没有效信号（含假名的串已由残留扫描覆盖）。

### 9.3 357 插件命令的参数里有资源文件名

- 形如 `.Image`（远景图文件名）、`.name`（SE 文件名，如 `決定ボタンを押す7`）
  的参数**看着像文本、其实是游戏内文件名**，译了就静默失效（远景图/音效消失）。
  正确处置：值写 identity（与原文逐字相同）+ 在 `allow_kana.json` 加**带锚点的
  正则**放行其假名；**绝不**新增白名单去掩盖真文本。
- 通用改进方向（中途改会让 seq 漂移，留到下次开工）：提取阶段跳过「与游戏内
  真实资源文件同名」的字符串（`img/parallaxes/<v>.png`、`audio/se/<v>.ogg`
  存在即跳过）——可运行时验证的启发式，不硬编码插件字段。

### 9.4 烘焙后残留扫描的「按设计跳过」必须逐条到引擎源码核实

- 在真实数据上迭代到**非文本命令零假阳性**才算可用：本作实测错误分类会多报
  约 2.8 万条噪声，校准后残留 61,252 条全为真文本。
- 已核实的类别（MZ，均查过 `rmmz_objects.js`）：657 插件命令参数回显（引擎读
  357 的结构化参数，不读回显）、205 `forceMoveRoute(params[1])` 路线脚本 +
  505 其回显、118/119 标签名（跳转按名精确查找，译了会断）、
  231/241/245/249/250 音画资源名、284 `changeParallax(params[0])` 远景图
  文件名、Actors 的 `characterName`/`faceName`/`battlerName`。
- 这一层是「提取器漏字段」的唯一捉虫点（见 §2c），所以跳过清单必须与提取器
  同步收紧，且扫描器要**打印**被排除的类别与数量，而不是静默 PASS。

### 9.5 插件参数内嵌 JSON 的豁免按「插件+参数」分类

- `plugin_json_leaves.py extract` 会捞到 UI 皮肤/样式/动画**标识符**（菜单皮肤
  插件按名精确查找）、SE 文件名、按键名、脚本里调用的插件命令名——全部必须进
  `--exempt`，否则译了菜单皮肤会失效。豁免文件是**每游戏本地产物**（不入库）。
- 生成方式：按 (plugin, param) 分类机械生成 `exempt.json`，再 `extract --exempt`
  复核剩余叶子数（本例 217 → 60，剩下的全是成就馆/图鉴/存档界面等真显示文本）。

### 9.6 blob 重建后写回构建（v1 合并路的 v2 等价物）

- v1 靠「合并进 translated.json」；v2 的译文库不含插件键，因此
  `plugin_json_leaves.py` 补了 `apply`（读 `plugin_blobs_translated.json`，
  复用 `translation.bake` 的 plugins.js I/O 写回），**跑在 translation bake
  之后**；原串在 plugins.js 里找不到的「死配对」会拒绝写入——那意味着叶子译文
  注定无效，静默写下去等于假装完成。

## 10. 插件参数的两个真盲区 + 图像日文政策（2026-09，实测漏译后回填）

本作（MZ，118 插件）已完成全量翻译、门禁五道全绿、构建扫描也过了，**但仍然漏了
3 条玩家可见的 HUD 标签**，全靠**实机试玩**才抳出来。两个盲区各自都会重现，
已分别修进工具：

### 10.1 盲区一：`DISPLAY_KEYS` 缺大写 `Text`

窗口构建类插件（ExtraWindow 等）把窗口标签存在 **JSON-in-JSON 的 `WindowList`
参数的 `Text` 字段**里（值也是嵌套 JSON 字符串）。`plugin_json_leaves.py` 的
`DISPLAY_KEYS` 原本有小写 `"text"` 而**没有大写 `"Text"`** → 这类窗口从未进
工作清单。教训：

- 插件参数的 display 键大小写不统一，**按「键名包含 Text/Title/Name/Message」
  的宽匹配收集、再用 `--exempt` 剔功能项**比穷举白名单安全。
- 实测漏掉的值：`引換券所持数\V[12]`（HUD 计数标签）、含 `園田晴香`/`宝来玲緒奈`
  的好感度窗口（均在小写/大写混淆下跑掉）。

### 10.2 盲区二：**无假名日文**——所有假名门禁的结构性盲区

`園田晴香`/`宝来玲緒奈` **整串不含任何假名**，只差字形 `園`/`緒` → 库门禁、
构建扫描器、执行者自查**全部看不见**。这是纯汉字日语（专名、UI 词、菜单词）
的固有漏洞，任何基于假名的检查都无效。做法：

- `qc_build_kana.py` 插件部分现除假名清单外，另出 **kana-free CJK 待复核清单**
  （`REVIEW` 行，**只报不算失败**），且把 JSON-in-JSON 参数拆成真叶子（共享
  `plugin_json_leaves.iter_string_leaves`，否则 2 KB blob 被截成 60 字看不到）。
- 验收必须**真看这个清单**并对照 `decisions.md` 人名表；本作两条就藏在这里。
- 反向验证：拿修复前的 `plugins.js` 嗂给新扫描器，三条全部命中（177 条待复核）。

### 10.3 图像里的日文不译（owner 定案）

标题 logo、UI 贴图、横幅、漫画式文字等**烧进图片**的日文属美术资源，**不在
翻译范围**，不必重画。判定方法（本次用于一条选择肢窗口上方的风格化日文横幅）：

1. 全树字节搜该串（UTF-8/CP932/UTF-16LE/`\uXXXX`）⇒ **0 命中**；
2. 运行时搜变量/事件名/插件参数 ⇒ 无；
3. 隐藏所有 `Sprite_Picture` 仍在、隐藏 `WindowLayer` 才消失 ⇒ 它是**窗口画**的；
4. 但文本不在任何数据/JS 里 ⇒ 只能来自插件运行时构造或图片合成 ⇒ 按美术放过。

先做前三步再放过，至少能区分「美术」与「真漏译」——本条与 8.1 两条的区别就是：
后者是**数据**（能改）前者是**图片**（不改）。

### 10.4 顺手发现的两个工具缺口（尚未修）

- `translation/bake.py::apply_font_mz` **只改 `mainFontFilename`**，不改
  `numberFontFilename` → 数字字体仍指向旧字体，`clean` 就不会把旧字体当
  “未使用”删掉（本例白留 8.8 MB）。手工把两者都置空后 `clean` 正常回收。
- `ExtraWindow.WindowList` 这类深层嵌套（三重转义）参数，`plugin_json_leaves`
  的 rebuild/apply 路径仍报 `dead pair`（够不到）→ 本次用受控字节替换完成
  （计数保护 + 改后重新解析 plugins.js 确认 118 插件仍在）。
