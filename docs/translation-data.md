# 翻译数据契约（RPG Maker MZ/MV）

本文件定义 v2 翻译流程读写什么：提取范围、键表与译文库格式、控制码规则、门禁
判据、构建扫描口径。流程与命令见 `docs/translation.md`；失败模式与故障排查见
`docs/translation-qc.md`。改动提取器或门禁前先读本文件，这里的表格就是「什么算
玩家可见文本」与「什么必须逐字一致」的权威。

## 1. 提取覆盖范围

`prepare`/`extract` 写入 `keys.jsonl` 的范围是引擎真正显示给玩家的字符串：

| 覆盖 | 说明 |
|---|---|
| `401`/`405` 正文 | 消息文本，含续行 |
| `102` 选项 + `402` 分支标签 | 选项列表与它的分支重复标签，两处都要译，否则插件显出日文 |
| `101` 参数[4] 名牌 | Show Text 的说话人名栏；只取 `parameters[0]` 会静默丢掉全部名牌（实测一款游戏 1,800+ 条、10k 个 id） |
| note 标签载荷 | 插件把标签载荷当文本显示时才提取（如帮助窗扩展、道具分类页签名），标签名本身不进键；`--note-tags` 打开，默认关闭 |
| 注释命令载荷 | 注释命令 `108`/`408` 里块状写的同名标签（用 `<Name>` 与 `</Name>` 包起来）与行内 `<Name: 值>`；常见事件菜单类插件把菜单项的名称、帮助、子文本放在这里（不是 `note` 字段），不提取就会留下玩家可见日文；同一个 `--note-tags` 打开 |
| `357`/`657` 插件指令 | 只取散文参数：插件名、命令名、JSON 参数对象、路径、脚本片段一律丢弃。参数对象内部的字符串也算，`{"messageText": "叫び声が響く……"}` 是弹窗文本，`{"text": "Shift 键快进"}` 是界面提示 |
| DB | `name`、`nickname`、`profile`、`description`，Skills、Items、Weapons、Armors 的 `message1`/`message2`，States 的 `message1..4` |
| System | `gameTitle`、`currencyUnit`、`types` 与 `terms`，以及 `switches`/`variables` 的名字（变量窗口插件会把 `$dataSystem.variables[id]` 画在界面上） |
| 不提取 | 注释 `108`/`408`、`Animations`/`Tilesets`/`CommonEvents`/`MapInfos` 的 `name`（编辑器内部名）、`note`（插件命令）、`657` 插件命令续行、`357` 的 `parameters[2]` |

判定看假名或汉字：`KANA_RE` 是假名块区间（含半宽片假名字母，也含 `・`、`ー`
这类假名块标点），`CJK_RE` 是汉字区间。路径形状的串不提取；`db`/`ui`/`plugin`
类里脚本形状的串也不提取。

**note 载荷是显式开关。** `note` 默认整体不提取，里面绝大多数是插件命令、内嵌
JSON、按名查找的功能键，翻了会改坏行为。少数插件把标签载荷原样显示，那是玩家
可见文本；其中一类只翻一边就直接弄坏功能：道具分类插件把 `<itemCategory:…>`
与插件参数 `categoryList` 里的分类按名逐字比较，参数翻了、note 没翻，那批道具
在任何分类里都不显示（不是少翻一点，是整批东西从菜单里消失）。所以：

```bash
python -m translation.cli prepare <game_dir> <work_dir> --note-tags 拡張説明,itemCategory
```

- 标签白名单由调用者给出，工具不硬编码游戏数据；清单记进 `stats.json` 的
  `note_tags`。
- 每个标签每次出现一个键，id 形如
  `data/Items.json#[12].note#itemCategory[0]`；DB 记录与地图事件的 note 都
  支持，事件的是 `data/Map172.json#events[1].note#LB[0]`。出现序号保证唯一与
  稳定；`ja` 只是载荷，标签名不进键。载荷不含假名或汉字（数字、坐标）时自动
  跳过。
- `bake` 只替换该次出现的载荷，标签名与同一 note 里的其它标签逐字节不动；译文
  含 `<` 或 `>` 时拒写并报 skip，避免毁掉标签语法。
- 翻这类键前先 `rg` 那个插件参数值：它多半同时又出现在 `data/*.json`（含
  note）或事件注释里，两边必须同译或同不译。实例见
  `docs/experience-translation.md`。

**注释命令里的块状标签**是同一批白名单标签的第二种写法，写在注释命令
（`108`/`408`）里，行内形如 `<Name: 港町アストレア>`，块状形如：

```
108: <Name: 港町アストレア>
108: <Help Description>
408: ヘルプ本文（可以多行，一行一条注释命令）
408: </Help Description>
```

常见事件菜单类插件把菜单项显示的名称、帮助、子文本存在这里，而注释默认整体不
提取，于是这类玩家可见文本会「五道门禁全绿但菜单里还是日文」。规则：

- 键 id 形如 `data/CommonEvents.json#[1054].list[1]#Help Description[0]`；
  地图事件则 `data/Map001.json#events[0].pages[0].list[1]#Name[0]`。块状载荷
  整块一个键，多行用 `\n` 连接，换行数门禁照样生效。
- 只读注释命令。写在脚本（`355`）、消息（`401`）或插件命令（`356`/`357`）里
  的 `<Name: …>` 是玩家看不到的功能数据，永远不会变成键。
- 没有闭合标签的块一律跳过，不猜载荷到哪结束；载荷为空不产键。
- 写回只动载荷本身：标签行、兄弟命令、同一段里其它注释逐字节不动。译文行数与
  源块不一致时拒绝写入，因为编辑器一行一条注释命令，行数不符会静默丢行或多行。

## 2. 357/657 与 JSON 参数

MZ 的插件命令在数据里存成三层：`357`（`[插件名, 命令名, @text, 参数对象]`）、
每个参数一条 `657`，以及参数对象本身。

- `Game_Interpreter.prototype.command357` 的实现是
  `PluginManager.callCommand(this, pluginName, params[1], params[3])`，只有
  `parameters[3]`（参数对象）会到插件手里；`parameters[2]` 是命令的 `@text`，
  即编辑器里的按钮名，如「選択肢の表示」。
- 引擎没有 `command657`（未注册的 code 在 `executeCommand` 里被直接跳过）：
  `657` 是编辑器为了把长插件命令折行显示而写入的 `argName = value` 回显，一个
  参数一条，运行时既不读也不显示。

两者都不是玩家能看到的文本，所以一律不提取。某一款 MZ 实测里它们占了 55,811
键中的 26,355 条（47%）；若被翻译，把参数名（`選択肢リスト`）译成中文会让插件
按名查参数失败，这不是多翻一点，是会改坏行为。真正要译的是参数对象里的字符串
字段（`messageText`、`choices`、`message` 等），它们按 `parameters[3].<字段>`
的 id 照常提取。

**参数对象里的 JSON 值不得改结构。** 有些插件的参数是装在字符串里的 JSON，而且
可能套两层（`["{\"label\":\"戦う\"}"]`，写回时要当整体）。这类键翻译时只能改
字符串字面量，键名、数字、嵌套一律不动：少一个方括号，插件的 `JSON.parse` 就抛
异常，事件当场卡住，玩家看到的是选择肢窗口不出现。机器门禁会替你守这一关：
`structure_problems()` 对源头是 JSON 容器的键要求译文解析成同构的 JSON（字符串
叶子按类型比较、可自由翻译；叶子自身是 JSON 的再递归比对），不符就在 `append`
阶段整批拒绝，并在 `control_codes` 门禁里报出。

## 3. 假名口径与提取盲区

三层判定各用一套字符类，同一个字符在不同层的结论可能相反：

| 层 | 字符类 | `・`（U+30FB）、`ー`（U+30FC） |
|---|---|---|
| 提取判定（`mvkeys.is_candidate`） | `KANA_RE` 假名块区间 + 汉字区 | 算假名 |
| 译文库门禁（`rawlib.kana_problem`） | `KANA_LETTERS_RE` 字母类 | 不算残留 |
| 构建扫描（`tools/qc_build_kana.py`） | 字母类 + `ヽ`（U+30FD）+ 半宽片假名 | 不算残留 |

- 提取判定用宽类，因为它的问题是「这段文字要不要翻」；整行半宽写的台词
  （`ﾌﾞﾂﾌﾞﾂ……`）若被判成无假名就会当非文本丢掉。
- 残留判定用字母类，因为译文里的 `・`（中文并列）、`ー`（破折）、`゛`（拟声
  浊点）是合法内容，按它们计数会把完成品报成残留。
- 唯一的刻意分歧是半宽浊点 `ﾞ`（U+FF9E）：`rpgmaker.japanese.KANA`（KiriKiri
  与 TyranoScript 的残留检查用它）算假名，`KANA_LETTERS_RE` 视作符号。三套类
  的字符范围由 `tests/test_kana_ranges.py` 逐字符钉住。

**图像里的日文不译**：标题 logo、UI 贴图、横幅、漫画式文字等烧进图片的日文属于
美术资源，不在翻译范围内，不必重画贴图、也不必为它开特例。区分方法：文本数据
改完后实机仍显日文，且全树字节搜（UTF-8、CP932、UTF-16、`\uXXXX`）零命中，就
是图片或美术，按此放过。能改的仍然要改：插件参数里的 `引換券所持数` 这类 HUD
标签虽然也不惹眼，但它是数据，不是美术。

**无假名日文是假名门禁的结构性盲区**：只差字形的人名（`園` 与 `緒` 这类汉字）
整串无假名，于是库门禁、构建扫描、执行者自查全都看不见。因此：

- `tools/qc_build_kana.py` 在插件参数部分除假名清单外，还会输出无假名 CJK 的
  `REVIEW` 行（只报不判失败）。
- 给出 `--source <日文原版>` 时另有 `IDENTICAL` 清单：构建里与原文逐字节相同且
  无假名的串，汉字-only 的日文词（`購買`、`塩味`）就藏在这里，同样只报不判
  失败。
- 验收时必须逐条过这两份清单，对照该游戏工作区的 `decisions.md` 人名表；条目
  数量在几十到一两百，多为已是中文的值。漏译过的 `引換券所持数` 就属于这一类。

## 4. 键表与译文库

**`keys.jsonl`** 由编排者产出，执行者只读。每行一个 JSON 对象，字段：

| 字段 | 内容 |
|---|---|
| `id` | JSON 路径，如 `data/Map003.json#events[2].pages[0].list[7].parameters[0]`，跨次提取稳定 |
| `seq` | 故事序号 |
| `kind` | 键的类别（`map`/`common`/`troop`/`db`/`ui`/`plugin` 等） |
| `where` | 位置（`文件:行号` 一类） |
| `ja` | 原文，控制码按字面保存 |
| `speaker` | 该键的说话人（能判定时） |
| `prev`/`next` | 上下文相邻键 |

故事序 = MapInfos → 地图 → 事件 → 页 → 命令 → 公共事件 → 敌群 → DB → UI →
插件。同一场景的键相邻，按此顺序阅读与翻译才能保持场景连贯。

**`translations.raw.txt`** 是执行者的唯一产出，零转义：

```
@@@data/Map003.json#events[2].pages[0].list[7].parameters[0]@@@
原样译文（可真换行、控制码字面照抄）
```

断点就是最后一个完整头行；同一 id 后写的一条胜出。JSON 转义只在 `to-json` 阶段
做一次。值里的尾部换行是字符、不是填充：源文本以 `\n` 结尾时（MZ 的 item
`description` 就是这种字段），译文也必须以 `\n` 结尾，库与批次格式照原样保留。
手写批次尾部多出的一个空行不会被吞掉，门禁会以多一行报出。

**状态文件**在同一个工作区里：`progress.jsonl`、`memory.md`、
`decisions.md`、`pending.jsonl`，按需再加 `rewrites.jsonl` 与
`allow_kana.json`。执行者自管这些文件，磁盘为权威，所以新开一个全新上下文的
执行者也能接着做。

## 5. 五道硬门禁

`gates` 跑五道门禁，全绿才能烘焙：

1. **覆盖**：每条键都有非空译文。
2. **控制码**：控制码序列逐字一致，序列里每个 token 的括号形状也必须一致
   （`\nc<name>` 改成 `\nc[name]` 就是换了 code）。数值参数必须逐字一致，文本型
   参数必须翻译：`\nc<チンピラ>` 是名牌，玩家读到的就是它；`\px[200]`、`\N[1]`
   是指令参数。源头是 JSON 容器的值（插件参数里的 `choices` 等）另外要求结构
   同构，见 §2。
3. **假名残留**：只查可读部分，即控制码之间加上文本型参数。译文里确实需要保留
   假名的条目写进 `allow_kana.json`，每项给 `match`（字面串或 `re:` 正则）与
   `reason`。判定用字母类，`・`/`ー`/`゛` 不算残留。
4. **换行数一致**：译文里的显式换行数必须等于原文。MZ 消息文本与 DB 描述里的
   `\n` 是作者排版，一行一个窗口行，少一行就是静默截断（实测 42 个技能描述只译
   了第一行，假名门禁与控制码门禁都看不见）。
5. **待决清零**：`pending.jsonl` 每条都要有结论，状态取 `resolved`、`decided`、
   `wontfix` 之一；裁定用追加式关闭，历史保留。

`append` 与门禁共用同一套校验，且是全有或全无：未知 id、空值、控制码或换行数
不符、假名残留、JSON 结构不符，任何一条不过就整批不写盘，译文库保持原样。加
`--fix-leading` 时，先按原文补回漏掉的前导控制码（续行重复开头的控制码是最高频
手误，实测约 60% 的续行条目靠它补回）。两种情形不补：译文已经以某个控制码开头
（该不该是这个码只能由校验判断），以及前导控制码的参数带文本（把人名原样抄回比
缺码更糟）。

## 6. 构建扫描

「`gates` 全绿」只证明已提取子集译完，不等于构建里没有日文。完工前在最终构建上
跑一次全树扫描：

```bash
python -m tools.qc_build_kana <build> [--source <日文原版>] [--work <工作区>] [--limit N] [--json]
```

- 扫 `data/*.json` 的每个字符串，用字母类判残留，并按引擎规则把「设计上就不该
  翻」的串排除：
  - 注释命令 `108`/`408`。
  - 参数字符串是逻辑载荷或脚本的命令 `111`、`205`、`355`、`356`、`505`、
    `655`、`657`（`111` 是条件分支的答案串与脚本操作数，`205` 是移动路线
    `forceMoveRoute(params[1])`，`505` 是它在编辑器里的回显）。
  - 按名查找的跳转目标 `118`/`119`（Label / Jump to Label），译文会改坏跳转。
  - 资源名命令 `132`/`133`/`134`/`231`/`241`/`245`/`249`/`250`/`284`，以及
    `characterName`/`faceName`/`battlerName` 字段：值都能在 `audio/`、`img/`
    下解析成文件。
  - `357` 的派发键与编辑器标签：`parameters[0]`/`[1]` 是引擎查处理器用的
    `pluginName:commandName` 键，`parameters[2]` 是编辑器按钮名；`parameters[3]`
    参数对象照查。
  - `Animations`/`CommonEvents`/`MapInfos`/`Tilesets` 的内名、地图事件的内名，
    以及 `System.json` 的资源字段（`sounds[].name`、`title1Name`/`title2Name`
    等）。
  - 全部 `note` 字段。
- 判失败的项：`UNEXPECTED` 假名残留、`%N` 占位符数量与原文不一致、读不了的
  文件、残留的运行期文本键 `\T[id]`。退出码 0 才算过。
- 残留的运行期文本键意思是构建里放的不是文本而是键（`\T[键]`），靠随包的运行
  时字典或游戏自带 CSV 文本表在运行时解析，构建里没有解析它的运行时，玩家读到
  的就是键本身。用 `tools/resolve_text_keys.py` 把它落成真文本；v2 的 `bake`
  不做这一步。
- 按名称查事件的串（`findEventByName`、`<namePop:>`、`<TE:>`）单列一条
  `WARNING`：那里事件名是功能性的，查参数与事件名必须同译。
- `--work` 给出工作区时读入 `allow_kana.json`（作者名、固定写法）。
- 该扫描与库门禁是两层：门禁只看已提取子集，构建扫描能看到提取器漏掉的字段，
  也是跳过清单写错时的唯一捉虫点。
